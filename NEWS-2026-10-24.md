### 3.5 [VRAM] #3321: the 5x copy gap was cold page tables, not the bus

**Source.** Issue **#3321**, open, 9 comments, updated **2026-10-24T12:16:29Z**. 4× RTX 4090 (host↔device probe
**26.8 GB/s**), 566 GB RAM, `--kv k8v4 --kv-resident 524288`, conversation cache 384 GiB / 192 slots, long-context
multi-turn agent traffic. 2026-10-20 comment by the reporter, still the answer today.

- **The observation:** a 497K-token conversation turn shows **99.9998 % prompt-cache reuse** (497,428 reused + **1**
  read) and still costs **~8 s** - all of it the `gave back` + `takes` copies at ~5 GB/s, plus a ~3.5 s `park`.
- **The root cause, with a microbench on the same GPU** (256 MiB, `cudaMemcpyAsync` + sync per slice):

  | scenario | D2H bandwidth |
  |---|---|
  | pinned, reused | **26.3 GB/s** (matches the startup probe) |
  | pageable, reused ("warm") | 21.3 |
  | pageable, **fresh each pass** | **2.28** |
  | fresh + pre-touched (faults moved out of the timed section) | 22.3 |
  | fresh + `MADV_HUGEPAGE` | 11.5 |
  | pinned, fresh | 26.1 |

- **The mechanism:** `ConversationBuffer` segments (`std::vector<uint8_t>`, 16 MiB) were allocated per stage per
  QSA state and freed right after; under `MALLOC_MMAP_THRESHOLD_=1MiB` each is a fresh `mmap`, so the D2H pays a
  4 KiB fault plus a **per-page driver pin** for pages it then drops. The 2.28 GB/s cell reproduces production
  to a tenth: 602,933 tokens / 7.72 GB / 3,238 ms = **2.4 GB/s**.
- **The fix and its size:** reuse one `[stage][qsa]` shuttle image across turns + one thread per GPU for both the
  slot shuttle and the park captures. Simulation: **serial fresh 11.44 s → pinned-reuse 1.47 s → +one thread per
  GPU 0.40 s.**
- Also a correction against the issue's own first arithmetic: the real snapshot is **7.72 GB**
  (`snapshot_bytes`), not the ~19.5 GiB the layer-count estimate gave.

**Applies: as a rule and as a cheap local probe.** The rule: *a copy rate is a property of the allocation
pattern*, so any bandwidth claim from this box must say whether the buffer was pinned and whether it was fresh.
The probe: pinned-reused / pageable-fresh at 256 MiB on our card is a throwaway script, and it would tell us
whether the **60-70 % of measured bandwidth** our decode achieves (2026-10-20 arithmetic) is a kernel gap or a
page-fault gap. **Instrument:** a small `torch`/`cudaMemcpyAsync` script in the ComfyUI venv (torch 2.10.0+cu130,
Python 3.12.11 - already installed for the image track). **Cost:** no download, minutes of scripting.

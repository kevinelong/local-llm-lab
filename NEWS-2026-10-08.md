## Strata v0.1.41 (published today 12:14 UTC; v0.1.40.4 also today, 08:04)

Our pinned engine is the **0.1.40.3** tree (`staged-strata-20261007/engine-src-v0.1.40.3`). The new
release is aimed at exactly our regime - Windows, 12 GB card, model bigger than RAM:

- **"Windows, model bigger than RAM: prompts about twice as fast" (#1323).** The prompt reader asks the
  drive for several experts in one request and gives up the memory-mapped view once reads bypass the
  cache. On the *RTX 5070* PC prompt time fell **45-52 %**, and IQ3_XXS/IQ3_S with a RAM budget read
  4K-20K prompts **16-25 %** faster. This matters because our ledger failures were **prefill-bound**:
  measured today, the suite reads **43.6 tokens for every token written** (10.3 M read / 237 k written
  across 21 sessions), and our Strata ledger ran at 550-670 tok/s prompt against 6.5-9.6 tok/s decode.
- **Their own RTX 5070 + Q2_0 row, i.e. our exact card and pack**: prompt equal, decode +0.4 % (story
  +4.9 %) - with the note that setup's automatic expert cache already holds ~3,700 experts on the card,
  and that **`--expert-cache 1500` makes the same short prompts 15-27 % faster**. We run
  `--expert-cache auto` plus `--resident-budget-gib 12`.
- **`STRATA_ROUTE_RESIDENT=1` (opt-in)**: **+4.1 % decode on RTX 5070 with Q2_0, 6 of 6 pairs** - our
  exact combination. It changes the answers (KL 0.07), so it is a declared experiment, not a default.
- **RAM-resident prompts were 4-7x slower on the 32-thread SSD path (#1353)**: when ≥90 % of the
  in-place experts are in the page cache it now uses the few-thread profile. With 64 GB we may be far
  more RAM-resident than we were when the 32 GB numbers were taken.
- **Hung-engine watchdog (#1317, #1407)**: a request whose engine prints nothing for 90 s, uses no CPU,
  moves no disk bytes and has an idle GPU is ended and restarted (`STRATA_ENGINE_STALL_S`). That is the
  class our stalled sessions and `quota_unknown` stops belonged to.
- **`<function= NAME>` tool calls are now parsed (#1430)** - the tool-call-rescue family we examined and
  found unexercised in our transcripts.
- Pinned asset: `strata-windows-x64-cuda12.zip`, 198,572,838 bytes,
  `sha256:646ded0105aa5213a75e16621d559670d09dac26b5c720c9fd651ca83bdf14ec`.

## Item 1 executed: the 0.1.41 A/B set (in progress at the time of writing)

Nine ledger runs at the 64k / 12 GiB / budget-6144 declaration, three roots per arm, on the new
engine (`staged-strata-20261008/engine-src-v0.1.41`, BUILD.json 0.1.41, asset sha256 verified,
venv and configs preserved from the copied 0.1.40.3 install). All runs scored 70/70, so the
differentiator is the engine's own rates, read from its logs.

| Arm | n | cold prompt (9,854-token system prompt) | per-request rate (median) | GPU cache hit, first -> last |
|---|---|---|---|---|
| baseline 0.1.40.3, same declaration | 5 | 615.9-657.0 tok/s | 68.8-73.8 | 48.2 % -> 53.8-69.2 % |
| **A: 0.1.41, defaults** | 2 | 615.9 / 656.9 | 68.1 / 69.4 | 49.2 % -> 59.1-65.1 % |
| **B: 0.1.41 + `--expert-cache 1500`** | 3 | **579.6** (all three identical) | 62.9-71.4 | **41.0-41.3 %** -> 51.0-52.6 % |
| C: 0.1.41 + `STRATA_ROUTE_RESIDENT=1` (clean) | 3 | 643.2 (615.9-656.9) | 69.8 (68.2-71.8) | 49.3 % -> 62.0-62.5 % |
| (C, first batch, contaminated by B) | 3 | 579.6 | 64.9 | 41.3 % -> 46.8-52.7 % |

- **A is neutral**: the upgrade alone matches 0.1.40.3 on every rate, and its GPU cache holds **2,425
  experts against 2,407** (the buffer savings from #1454). Take the upgrade for the behavioural fixes -
  the hung-engine watchdog that addresses our stalled sessions, `<function= NAME>` parsing, q8_1 clamp -
  not for speed on this box.
- **B is a regression here**: the smaller expert cache costs 6-12 % on the cold prompt and 8 points of
  hit rate. The release note says the hint helps where the automatic cache is *bigger than useful*; our
  `--resident-budget-gib 12` already keeps the RAM side small, so shrinking the GPU side just streams
  more experts. Consistent with the note's own asterisk on the RTX 5070 row ("prompt equal" by default).
- The release's headline fix (prompts ~2x faster on Windows when the model is bigger than RAM) targets
  reads that *bypass the cache*, i.e. streaming experts from disk. Our prompt path is RAM-bandwidth
  bound: 620-657 tok/s is far above a disk-bound read, which is also why plain `--mmap-experts` put
  free physical at 1.92 GiB and was never runnable under the 3 GiB floor. The claim cannot apply here.

**Config-leak lesson (cost: a wasted arm batch).** The engine config file lives in the *engine install*
and is shared by every root that uses it, so an arm that does not state a value inherits whatever the
previous arm wrote - all six B/C runs showed an identical 579.6 tok/s cold prompt because arm C had
inherited B's `--expert-cache 1500`. The driver now declares the expert cache explicitly for *every*
arm (absent means the engine default) and the built config is read back before the run. The first
arm-C batch (vC1..vC3) is preserved with a README explaining the leak; arm C was re-run as vC4..vC6.

**Operational lesson (cost: one lost run).** A batch launched with a bare shell `&` is reaped when the
tool call that started it returns, so the loop that was to run C4..C6 stopped after C4 finished and
never built C5/C6 - and the killed loop died between a run completing and its record being written, so
C4's metrics had to be recovered from its artifacts with the driver's own `metrics()`. Batches now go
through the harness's background-job mechanism, which reports on completion.

## Overnight (2026-10-08/09): the Swift batch died on a usage gap, and two new instruments were built

- **`quota_unknown` cost a whole batch.** The Swift six-task re-baseline aborted after 122 s with
  `AssertionError('OMP native read smoke failed')`: the host smoke's session had been terminated at
  31 s (`exit_code 143`, `interrupted: quota_unknown`, `final_text` empty, one user turn and no
  assistant turn). The relay marks `quota_unknown` when a response carries no usage, and the harness's
  `execute()` loop stops a session on `budget.failure`. This is the **third** place that gap has bitten
  (runner sweep guard, Strata session, now a llama.cpp session), and the fix is at the **relay**:
  `_BudgetUsageTolerant` now counts the gap instead of failing, injected into every new-task root and
  into the already-built Qwen3.6 root in place. A runner-level guard protects the sweep, not the session.
- **`repo2`** (55 checks, four independent defect classes; reference 55/55, starter 34/55) and **`perf`**
  (33 checks, two graded scale tiers + correctness; reference 33/33 in 5.5 s, quadratic starter 31/33
  failing only the scale tiers) are authored, verified offline and wired into the driver, but kept out of
  the six-task loop so tonight's batches remain comparable. `perf` adds an axis no other task measures -
  whether the model notices a complexity requirement - with the scale tiers in a timeout-guarded
  subprocess so a quadratic candidate cannot hang the scorer past its 30 s limit.
- **Task-discrimination census** (`local-llm-lab/TASK-DISCRIMINATION-2026-10-08.md`): with a
  leave-one-out, top-group-scoped count, `events` has **5** live checks and `paths` **2**, `ledger` 13,
  `ledger2` 40, `repo` 3 (one bug class) and `longctx` **0**.
- **The Bespoke `civil_comments` anomaly is solved** (`local-llm-lab/BESPOKE-METRIC-2026-10-08.md`): the
  subset is 32-positive-of-300, so its majority baseline is 89.3 % and our 91.0 % is that baseline plus

  takes the top spot from nimble 9B.

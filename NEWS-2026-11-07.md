## 1. [REL] Strata v0.2.12 / Engine 0.1.58: what a 12 GB card actually gets

Read in full at the release page. Published **2026-11-07T08:54:40Z**, created 08:24:51Z, `prerelease: false`, **42 assets,
9.70 GiB**, feed sequence 122, tag commit **`146df3c`**. App and Terminal **0.2.12**; **Control and every engine package
0.1.58**.

### 1.1 The three rows that touch a 12 GB card

| Machine, model | Prompt | Output |
| --- | --- | --- |
| RTX 3060 12 GB, UD-IQ4_XS-v31 | **2K 87 -> 264**; **32K 361 -> 981** | code **+37 %**, agent **+34 %**, **JSON -18.9 %** |
| Strix Halo, UD-IQ4_XS-v31 | 4K 690 -> 1,220; 32K 1,107 -> 1,377 | code +10 %, chat +3 %, **tool call -9.5 %** |
| Radeon R9700, IQ3_S (Auto now MTP) | 32K 3,076 -> 3,304 | **code -10.5 %, tool call -9.3 %** |

Method, in the release's own words: 0.2.11 and the 0.2.12 candidate side by side, **2 to 3 rounds, a fresh engine start
per run, the arms swapped in order each round, greedy answers of 300 tokens**, each version using the settings it writes
for that machine. And the two declarations that bound every number: **"speeds were not measured again on the final 0.1.58
packages; the engine source after the check changed only in the version number and two build fixes for old NVIDIA cards"**,
and the 3060 is **Linux** for the file-tier item below.

**Applies to us:** partially and specifically. Our card is an **RTX 5070 12 GB, sm_120, Windows** - the same VRAM class
as the quoted 3060 (sm_86), a different architecture and a different OS. The 3060's 3x prompt gain is on
**UD-IQ4_XS-v31**, a pack we do **not** stage; our pack is `q2_0`, and the release's Auto rules are named per quant.
**Instrument:** our existing chunk ladder (`control/chunk_ladder.py`) plus the resident ladder, at a declared
`--prefill` and with the engine's own chunk line read back. **Cost:** one gated download (`windows-x86_64-cuda-cuda13`,
**630,769,464 B** at 0.1.58 against 627,812,560 at 0.1.57 and 627,806,827 at 0.1.56, so **+2,956,904 B**) and one ladder.

### 1.2 The item that is worth more than the speed rows: the start-up check stopped lying

Verbatim: **"12 GB cards (Linux): the second start-up check no longer counts the engine's own memory as free, so it stops
switching to the slower file cache. When it still switches it says: `strata: expert reads now go through the file cache
(X GiB of RAM free for them, Y GiB limit)`. On the RTX 3060, 0.2.11 switched in 3 of 3 starts and 0.2.12 in 0 of 3.**"
Back-out: `STRATA_FILE_TIER_HONEST=0`.

That log line is the file-tier equivalent of the line our gate already demands. We have measured what the file tier costs
when it takes over: on 2026-10-27 only the two arms the engine called *"the file cache can keep them"* cleared 20 tok/s
decode (**23.1** and **87.0**) against **4.1-16.6** for the eight unbuffered ones. So a check that mis-decides this
switch is worth an order of magnitude, and it was mis-deciding **3 of 3** on a 12 GB card.

**Applies to us:** the item is scoped to **Linux** 12 GB cards; our engine is the Windows CUDA 13 package. Whether the
same check runs on Windows is **not stated in the release** and is not claimed here. What it buys us is a **declaration
field**: read the file-tier line out of the log, and mark the arm's tier in the arm JSON - the same treatment
`resident_pinned: true` gets.

## 2. [GH][VRAM] llama.cpp: the pinned buffer is reallocated every request, measured on a 5070

This is the strongest item in the window for this box, because the reporter's machine is our machine.

### 2.1 `#31840` - the measurement

Created **2026-11-07T06:16:50Z**, 0 comments, open. Environment: **v0.9.0 tag, commit `cd959bae99`, build 1**,
**Linux x86_64, RTX 5070 12 GiB (SM120), Ryzen 5 7500F, NVIDIA driver 595.99.02**, CUDA Toolkit 13.4, `GGML_CUDA=ON`,
`GGML_CUDA_GRAPHS=ON`, `CMAKE_CUDA_ARCHITECTURES=120`, Nsight Systems 2026.3.2. **No speculative decoding and no draft
model** - the backend sampler is attached and then removed.

With `--backend-sampling`, requests completing at different times make the server detach their samplers; the next decode
re-reserves by **recreating the scheduler and its allocator**, freeing and reallocating compute buffers including an
**approximately 80.02 MiB `CUDA_Host` buffer**. In one batch of 32, after an additional 32-request warmup:

- `cudaMallocHost`: **33 calls, 1.043083 s**; `cudaFreeHost`: **33 calls, 0.365828 s** - all returned success, so this is
  churn, not a fallback to pageable memory.
- **32 fully captured `sched_reserve` calls longer than 1 ms totalled 1.433764 s**, *"all overlapping periods with no
  recorded GPU kernel/memcpy/memset activity"*.
- All 32 requests returned HTTP 200, exactly **16,432 input / 17,085 output tokens**, no cancellations.

### 2.2 `#31841` - the patch and its price

Created **2026-11-07T07:01:34Z**, 0 comments, open. Fixes `#31840` by **keeping the existing scheduler when its node
capacity is sufficient** and recreating it only when capacity grows; graph invalidation, synchronisation, allocation
planning and the pipeline-parallel fallback stay. New test `test_sampler_buffer_reuse` *"fails before the change and
passes afterward on both CPU and CUDA"*.

| Complete workload (256 requests, 8 batches of 32, extra 32-request warmup excluded) | Baseline | Patched |
| --- | ---: | ---: |
| Run 1 / 2 / 3 | 70.664470 / 70.476790 / 70.521613 s | 59.234996 / 59.109644 / 59.126150 s |
| Mean | **70.554291 s** | **59.156930 s** |

**-16.15 % wall**, all six runs **256/256** length checks with 133,966 output tokens each, no parameter changed between
builds. First-32-request diagnostic: `cudaMallocHost`/`cudaFreeHost` **33/33 -> 0/0**, cumulative `sched_reserve`
**1.435 s -> 0.042 s**, and a full-lifetime trace confirmed pinned allocations still happen before the measurement
window - *"this does not disable pinned memory"*.

**Why this is more than a llama.cpp item.** It is a **third independent mechanism** for two things this lab already
records: *a rate inherits the machine's prior workload* (2026-10-20, when q1's arms differed only by what had run 42 s
earlier) and *commit headroom decays inside a run* (2026-10-31, 24.87 -> 13.91 GiB over 24 starts). A pinned allocation
that is freed and re-taken 33 times per batch is invisible to every tok/s instrument and visible in commit and in the
WDDM shared segment - which is the number our gate reads.

**Applies:** directly in mechanism, not yet in code. We run `--parallel 1` and no `--backend-sampling`, so **our arms may
not trigger this path at all** - the reporter's trigger is *"backend sampling ... attach and remove"*. The check is one
log/scheduler line and one Nsight-free proxy: count `cudaMallocHost` (or read commit churn) across a multi-request run.
**Instrument:** `orphan_check.py` extended to sample commit **during** a run rather than before it, plus the existing
ladder. **Cost:** no download (the mechanism can be probed on b11480), but the patch needs a build at **>= b12189**.

### 2.3 `#31447` merged - the meta compute view limit goes 16 -> 256

Merged **2026-11-07T03:05:24Z** (commit `fd27b20`), 0 comments. With `-sm tensor`, DeepSeek-V4.1 aborted on the first
decode: `ggml_new_object: not enough space in the context's memory pool (needed 12144, available 11776)`. Cause, named
with line numbers: compute containers holding external views of a meta buffer have room for **16 views per statically
allocated tensor**, and DeepSeek-V4.1 **shares the KV cache of a source layer with the following layers** - in the 1017
checkpoint (`kv_source_layers` = 2, 8, 14, 20) layer 20's cache is read by layers 20-39 **and** by the indexer candidate
path, so **46 views** of a buffer that holds only two static tensors are created before the container is reset. Fix: at
least **256 views** per container, *"at most 2 x 8 x 256 x 368 bytes = 1.5 MB of tensor metadata per meta buffer"*.

**Applies to us:** only if we ever run `-sm tensor`, which we do not. What it earns is a declaration rule: **a shared-KV
architecture has a view count that is a property of the model file** (`kv_source_layers`), and the limit it hits is a
memory-pool assertion, not an OOM. Recorded because a `not enough space in the context's memory pool` line on a
DeepSeek-V4.1 pack is this, not the WDDM gate.

### 2.4 `#31802` open - the fused q8_0/q4_0 KV dequant is the answer to our FA_QUANTS gap

Created **2026-11-06T12:39:40Z**, **6 comments**, updated 2026-11-07T11:21:46Z, **still open**. *"For quantized KV,
flash-attention currently runs a separate dequantization pass that materializes the full K/V as f16 in scratch memory
before the MMA kernels can read it"*; this fuses the conversion into `fattn-mma-f16` for **q8_0 and q4_0**, and honours
`#29510`'s `flash_attn_ext_rows` gather so it stays correct with kv-unified multi-slot serving.

Measured on **3-4x RTX 2000 Ada (sm_89)**, P2P over PCIe 4.0 x8, branch vs pure master at the same trunk commit, q8_0 KV:

- **Decode at depth**: 27B Q8_0, no-spec, 3-GPU tensor split - **+17.6 % (32k), +33.9 % (64k), +63 % (131k), +79 %
  (171k)**; prompt processing within **+2 %**; with the fused kernel off, the branch **ties master bit-for-bit at every
  depth**.
- **End-to-end serving**: 35B-A3B MoE, 32k prompts, streaming, aiperf - **decode +21.7 % with spec off, +11.3 % with
  draft-MTP on**; prefill **+1.1 %**; **VRAM -496 MiB/GPU at np1**, -480 MiB meta buffer at np4/ub1024.
- Frees **~0.5-1 GiB/GPU** by removing the f16 FA scratch; on that box that is *"the difference between the 262k/np4
  preset loading or OOMing on 3x16 GiB"*.

**Applies to us:** this is precisely the gap recorded on 2026-10-25 - *"a quantised-KV row must name the binary's
FA_QUANTS"*, and the default Windows CUDA build does not carry the `q8_0-q4_0` pair, so it silently converts to f16. The
PR **removes the need for that compile flag** rather than documenting it. Not merged, so it changes nothing today; what
it changes is the **target name** for any future build, and the expectation that a quantised-KV row's price is a scratch
buffer of ~0.5-1 GiB, not just bandwidth.

### 2.5 `#30779`, `#31842`, `#31850`, `#31803` - the rest of the in-window code

- **`#30779` merged** (commit `0956684`, 2026-11-07T11:03:38Z): *"server: visit parent slots before child slots"*. Slot
  parentage is how shared prefixes are ordered, and our rows are cache-sensitive (`reused` and `N checkpoints` are
  declaration fields since 2026-10-26).
- **`#31842`** (created 2026-11-07T07:06:55Z, 0 comments): **`ggml_vec_dot_bf16` casts the activation vector to BF16 and
  unpacks it back to FP32 inside the innermost loop, for every row**. On one Skylake core, **ALU/L2/L3 1.32x -> 1.47x,
  DRAM streaming 1.06x**, and **relative error vs FP32 falls from 1.24e-04 to 2.28e-08**. The reporter's own framing is
  the useful part: *"the CPU was super happy to not do the casts in the hot loop."* **Applies:** our `--cpu-moe` runs CPU
  expert kernels; a bf16 CPU path is not our quant type (we run Q4_K/Q2 GGUF), so this is a **numerics-plus-speed
  witness** that a kernel can be both slower and less accurate than it needs to be - the class `#31803` also belongs to.
- **`#31850`** (created 2026-11-07T09:27:08Z, 1 comment, draft): an **optional dedicated upload stream** for expert H2D
  copies (`GGML_CUDA_UPLOAD_STREAM=1`), `GGML_SCHED_COPIES`, and a `GGML_MOE_TRACE` counter of uploaded/cached bytes per
  node. **No speed-up is claimed**: KAT IQ4_XS, q4_0 KV, `-ub 8192`, `ncmoe 30` at 96k and 128k reads
  **987.3/23.3 off vs 985.9/23.2 on** and **979.3/23.5 vs 986.7/23.8**, answer SHA `a672c953` identical. The value is
  `GGML_MOE_TRACE`: **uploaded bytes per node** is the engagement proof our cache rows have always had to infer from
  VRAM readback (2026-10-20, q2c). **The first version had a real bug** - it did not track in-flight copy events, so a
  later upload could overwrite a ring slot the compute stream had not consumed; the fix waits on each slot's event.
- **`#31803` merged** (commit `5d7d4ae`): *"CUDA: fix shared memory bank conflicts in the lightning indexer"*. No numbers
  in the commit title; the lightning indexer is the sparse-attention path DeepSeek/GLM use, and **`#29050` (CDNA2 MFMA)
  and `#30156` (SYCL device-side MoE scheduler) are the same axis on other backends**. Recorded at title level only.

### 5.1 `2611.08363` StrataFlux - the paper that prices our pack's regime

Submitted **5 Nov 2026**. Not the engine; the name is a coincidence.

> *"Quantization reduces the memory and bandwidth demands of large language model (LLM) inference but can degrade
> accuracy; offloading higher-precision data can instead stall generation. We introduce StrataFlux, a framework that
> challenges this tradeoff by recovering accuracy lost to low-bit weight and key-value (KV) cache quantization while
> retaining quantization's memory and speed advantages. StrataFlux co-designs refinement representation, selection, and
> delivery to make **host RAM and solid-state drives useful sources of additional precision**. Its selective precision
> streaming reduces transfer volume, overlaps delivery with computation, and **reuses fetched precision across decoding
> steps** so generation need not wait for every transfer."*

Results, in its own terms: evaluated on **2-4-bit weights and 2-3-bit KV cache** on dedicated GPUs and unified-memory
platforms; **2-bit Llama-3.1-8B-Instruct: WikiText-2 perplexity 9.46 -> 8.40 while keeping 95.4 % of the quantized
base's throughput on RTX 5090**; **2-bit weights and KV: Qwen3-8B AIME 2024/2025 11.0 % -> 47.1 % at unchanged GPU
memory use**.

**Applies:** our staged pack is `q2_0` and our engine's whole design *is* "host RAM and SSD as tiers". Two consequences.
(1) **The 2-bit quality floor is not a property of 2 bits** - a 4.3x AIME recovery at the same VRAM means a q2_0 row's
task score is partly a property of its *delivery* design, so "our pack scored X on the 414" is a statement about the
engine too. (2) **The instrument this needs is a task-level arm, not perplexity** - the lab's rule since 2026-10-29.

### 5.2 `2611.07605` - a gate trained on the model's own loss prefers to do nothing

Submitted 5 Nov. A learnable gate on each cached entry's attention weight, **inside the normalizing softmax** so
suppressing one entry hands its mass to the others; *"that same normalizer absorbs any per-query constant, so a constant
gate cancels and reproduces the frozen model exactly"*. Trained on the LM loss, **the gate stays near a constant score
while its loss falls throughout**: *"optimization succeeds, but a frozen backbone was fit for dense attention, so its loss
prefers the no-op."*

**Applies:** this is the formal reason an eviction or sparsification arm can report a falling training metric and no
behavioural change - and it is the same shape as our own null results (`NEWS-2026-10-30`: the `STRATA_STAGE_TRIM=1` "null"
that was really *ignored*). Instrument implication: **an approximation's harness must assert it fired**, not that it
trained.

Also read at abstract level: **`2611.07263` HyFlash** (a prefix-memory prior separating long-range context from
draft-position interaction for on-device parallel drafting: local attention plus a recurrent fixed-size state);
**`2611.07217` TileQuant** (precision assigned to hardware-aligned 2D weight tiles, because column-wise mixed precision
retains insensitive weights too).

**The method.** *"Every word is first computed on a 2-bit copy of the model's experts. When the model itself is unsure

correction plane."* The gate is the **top-2 logit gap under 0.45**. Four parts: the 2-bit copy; the confidence gate; the
correction plane (2-bit -> exact FP4); and the model's own draft head checked *"in parallel lanes, which spreads the cost
of reading experts across several words"*, with the most-used experts in VRAM and the rest in RAM and on two drives.

**The numbers, with the author's own limits.**

| **2-bit copy alone, before correction** | **97.40 %** | 96.98 % |
| GSM8K, 10 problems | 9 correct | 9 correct |

They declare: *"No prompt reaches the 8 tokens/s milestone we set"*; first-word time is read-bound (**~126 s on a

covers **three prompts of 30, 76 and 1,163 tokens**; each long-prompt audit is **one run**; **one machine, one model, one
prompt family**.

**The hardware line that decides it for this box:** *"one NVIDIA RTX 30 or 40 series card with 12 GB (compute capability

**Applies:** not runnable here as shipped. What transfers is the **instrument**: a **decode-time confidence gate** is a

correction on and off - which requires an engine that has the gate, and neither of ours does.

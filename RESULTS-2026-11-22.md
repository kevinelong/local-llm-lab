# Quality pass 2026-11-22: Inkling 2 Mini against qwen3:8b and qwen3:14b

Ten tasks, three runs each, one scorer, temperature 0. The purpose is to decide whether a 26.4B/3.4B-active IQ2_XXS
model earns the general slot the store's table gives to `qwen3:8b` / `qwen3:14b`, or whether it only keeps the
capabilities those two do not have (vision).

Harness: `benchmarks/quality-pass-2026-11-22.py` (written for this pass). Raw replies for every run are in
`results/quality-*-2026-11-22.json`; the scorer is in the same file as the tasks, so a reader can re-score by hand.

## The tasks

| task | what it asks | how it is scored |
|---|---|---|
| `bat_ball` | bat-and-ball, the classic trap | the **first sentence** must say $0.05 (a later explanation that names $0.10 does not fail it) |
| `planets` | eight planets in order, one per line | the eight names appear in order |
| `extract_count` | crates in a four-fact passage | `12` present |
| `json_shape` | only a JSON object, `n`=3 and three lowercase words | parses; shape validated |
| `exactly_five_words` | describe rain in exactly five words | word count is 5 |
| `code_is_prime` | `is_prime(n)` in one fenced block | **executed** against 2, 3, 4, 17, 25, 97, 1, 0, -7 |
| `needle` | a code buried in a ~350-token passage | `Azure-4471` present |
| `count_letters` | r's in "strawberry" | `3` |
| `no_invention` | a moon landing on an exoplanet's moon | must decline; an invented year fails it |
| `summary_20` | summarise in at most twenty words | word count ≤ 20 |

Two scoring bugs were found and fixed **before** the published numbers, both of which had read as model failures:
`bat_ball` rejected any reply that mentioned $0.10 anywhere (qwen3 explains where $0.10 comes from after answering
$0.05), and `no_invention` did not recognise "no crewed landing … has occurred" as a decline.

## What the pass says, and what it does not

**It says** the 2.06 bpw quantisation did not cost measurable correctness on these ten tasks: the arithmetic trap, the
ordered list, the two exact-number extractions, the JSON shape, the executed `is_prime`, the buried code, the count,
and declining an unknowable fact all came out 3/3, and the model hit a hard length constraint that both dense
references missed. That is enough to remove "the aggressive quant makes it unreliable at simple work" as a reason to
keep it out of the general slot.

**It does not say** Inkling writes as well as a 14B dense. Ten mechanical tasks are a floor, not a ranking: they are
chosen so a script can grade them, which means they reward exactness rather than the prose, tone and multi-step
judgement a general daily driver is actually chosen for. A 100 % here is "not worse at the checkable things", and the
honest summary of the head-to-head is **a tie with one point in Inkling's favour**, not a win.

**It does not measure** long context: this box's Ollama serves both `qwen3` models at **32,768** tokens (`ollama ps`),
the same window as Inkling, so the needle at ~350 tokens sits far inside all three and proves nothing about the
window. A real long-context comparison is a separate run with longer needles.

**Speed is not a quality result**, and today's numbers are contaminated anyway: the first Inkling pass ran on a
server instance that had degraded from 52 to 5.4 t/s (the same fresh binary then measured 57.4 t/s from the CLI), so
its timings are not usable and only its verdicts are. Rate work stays in `INKLING-2-MINI-2026-11-21.md`.

## The trap this pass nearly published

The first run of this battery scored qwen3:8b at **13/30** and would have "proven" that a 14B-class model is worse
than a 2 bpw MoE at basic work. Both causes were mine, not the model's:

1. `max_tokens 640` cut qwen3's reasoning at 1,900-2,650 characters (`finish=length`, empty content). At 2,048 the
   same model scores 27/30. A budget that fits one model's thinking style and not another's is a harness difference
   dressed as a capability difference.
2. Two scorers were wrong: `bat_ball` rejected any reply that mentioned $0.10 *anywhere* - including the explanation
   a correct answer gives for why $0.10 is wrong - and `no_invention` did not recognise "no crewed landing … has
   occurred" as a decline.

Every published row was then produced by **re-scoring the stored replies** with the fixed rules
(`benchmarks/rescore-2026-11-22.py`), so the comparison rests on one scorer version over identical model output. The
first, wrong numbers are kept in the log history rather than deleted: `13/30` at 640 tokens is what a truncated
budget looks like, not what qwen3:8b can do.

## Speed, measured separately and fairly

`benchmarks/speed-probe-2026-11-22.py`: one prompt, `max_tokens 400`, temperature 0, a warmup call, three measured
runs, throughput from the server's own `completion_tokens` over wall time. One model loaded at a time.

| model | placement (`ollama ps` / buffers) | resident | generation tok/s (median of 3) |
|---|---|---|---|
| qwen3:8b (Q4_K_M, 9.8 GB) | **100 % GPU**, ctx 32768 | 9.8 GB | **102.4** (102.2, 102.8, 102.4) |
| **Inkling 2 Mini (IQ2_XXS, 7.9 GiB)** | **100 % GPU**, 32K, 11.7 GiB | 11.7 GiB | **67.4** (67.4, 67.4, 67.4) |
| qwen3:14b (Q4_K_M, 14 GB) | **38 % CPU / 62 % GPU**, ctx 32768 | 14 GB | **19.1** (18.9, 19.1, 19.3) |

This is the store's own lesson measured on one day with one probe: **the 8B dense is the fastest thing here and the
14B is the slowest, not because of its parameter count but because it no longer fits** - 14 GB into a 12 GB card
spills 38 % onto the CPU and loses 5x against the 8B, while a 26.4B model that fits (2.06 bpw) sits between them at
67 tok/s.

Two corrections this probe forced on earlier notes: `MODELS.md`'s "60-70 tok/s" for 12-14B dense was measured at a
smaller context than the 32K this box's Ollama now picks, and the quality pass first recorded Ollama as running at
4,096 - `ollama ps` says 32,768 for both.

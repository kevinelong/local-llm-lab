# Local AI lab: next experiments

Research date: 2026-09-15. These are candidates and proposed experiments, not new benchmark results.

Execution followed this research: Pi and two selected GGUF variants were installed and tested. See [RESULTS-2026-09-15.md](RESULTS-2026-09-15.md) for measurements, failures, and what remains untested. The observations below describe the initial research state.

## Observed local state

- RTX 5070: 12,227 MiB total VRAM; 2,275 MiB used during inspection. Driver 610.60; Ollama 0.34.0.
- Ollama had no resident models. No inference workload was visible in the NVIDIA process list. Desktop applications accounted for the visible GPU processes; per-process memory was unavailable under WDDM. No processes were killed, models downloaded, or inference tests run during this research.
- Installed baselines include qwen3.5:9b, qwen3-coder:30b, gpt-oss:20b, and granite4.2:8b. Pi was not found on this shell's PATH.
- Existing hard-spec result: Aider architect plus qwen3-coder:30b scored 8/10. The useful target is fixing cycle detection and self-test failures, not another FizzBuzz run. See HARD-SPEC-TEST.md.
- Prior Flash Next logs show an Ollama import failure: one shard was seen where three were expected. That attempt does not establish usable performance. Download completion and successful inference are separate checks.

## Recommended order

1. Add Pi to a controlled comparison with Aider and OpenCode using the already-installed qwen3.5:9b. This isolates the agent's effect before downloading more weights.
2. Test Tesslate OmniCoder-9B Q4_K_M against base Qwen3.5-9B at matched context and quantization; try Q6_K only after the initial comparison.
3. Test Nanbeige4.2-3B with a verified compatible runtime as the compact-agent challenger.
4. Establish CPU-only baselines with LFM2.5-1.2B and Microsoft BitNet; add Ternary Bonsai after verifying its custom kernel/build support on x86 Windows.
5. Try one larger MoE, starting with North Mini Code or Laguna XS 2.1. Qwen3.6-35B-A3B is another candidate, but its default 23 GB download puts more pressure on 32 GB system RAM.
6. Run a useful local document-search experiment using embeddings, then a CPU transcription experiment.

All fit assessments below are estimates. Weight-file size excludes KV cache, scratch buffers, and desktop overhead. Few active MoE parameters do not guarantee fast CPU offload.

## Models that can avoid the GPU

CPU-only operation is possible for conventional models too. The distinctive new experiments are architectures and kernels that make it more practical.

| Candidate | Proposed task | Evidence and limitation |
|---|---|---|
| [Microsoft BitNet b1.58 2B4T](https://huggingface.co/microsoft/bitnet-b1.58-2B-4T) with [bitnet.cpp](https://github.com/microsoft/BitNet) | Small reasoning/extraction baseline | Native ternary approach with optimized CPU inference. Windows build instructions require CMake/Clang and VS developer tools. Benchmark locally; no claimed speed on our CPU yet. |
| [Prism Ternary Bonsai 8B](https://huggingface.co/prism-ml/Ternary-Bonsai-8B-gguf) | CPU general assistant and code probes | 2.18 GB packed weights; card reports CPU operation. Its Q2_0 format needs Prism's llama.cpp fork according to the card. Published Apple CPU speed does not establish Windows/x86 speed. |
| [Liquid LFM2.5-1.2B-Instruct](https://huggingface.co/LiquidAI/LFM2.5-1.2B-Instruct) | Structured extraction, routing, grounded answers | Publisher provides CPU benchmarks and recommends extraction/RAG/agentic uses, but explicitly does not recommend programming or knowledge-heavy work. |
| [BitNet Embedding 0.6B](https://huggingface.co/microsoft/bitnet-embedding-0.6b) | Search lab notes locally | CPU-optimized embeddings; publisher benchmarks use Xeon, not our desktop. Compare retrieval accuracy and latency with Qwen3 embeddings. |
| [VibeVoice-ASR-BitNet](https://huggingface.co/microsoft/VibeVoice-ASR-BitNet) | Transcribe a fixed audio sample | CPU-focused speech recognition, about 1.58 GB combined weights. Measure word error rate and real-time factor locally. |

NPU inference is another GPU-free path, but it is not CPU-only. [OpenVINO supports Intel NPUs](https://www.intel.com/content/www/us/en/developer/videos/prototype-deploy-llm-applications-on-intel-npus.html); detect the exact installed device/driver and validate model support before planning this track.

CPU test protocol: use explicit CPU backend configuration (for example a CPU-only llama.cpp build and zero GPU layers), verify backend logs and no model VRAM allocation, and compare 8/16/24 threads. Record first-token latency, prompt throughput, decode throughput, RAM, and correctness. Avoid concurrent CPU-heavy jobs.

## Pi and the test harness

[Pi's current upstream documentation](https://github.com/earendil-works/pi/tree/main/packages/coding-agent) supports llama.cpp routing, custom compatible providers, Windows PowerShell tools, and noninteractive runs. Pi is a coding agent; our external evaluator remains the judge.

Proposed comparison: Pi, Aider, OpenCode; same local model/quantization, backend, context, task, and time limit. Begin with one smoke run per agent, then three fresh-workspace trials for promising combinations. No cloud fallback. Record prompt/tool format and reasoning handling so adapter failures are visible.

Use examples/spec2.md and examples/eval2.py for continuity. Keep evaluator code outside the agent's writable task directory, freeze it, and give every agent the same public checks. Score first pass and final output, elapsed time, tool-call success, retries, tokens, and human intervention. Pin package versions. Inspect differences in Aider architect/edit models rather than labeling a mixed-model run as a single-model comparison.

Add two held-out tasks after the existing spec: repair a seeded dependency-cycle bug in a tiny repository; recover from a controlled tool error. Existing 8/10 is a single historical run, not a reliable model capability ceiling.

## Pre-test cleanup procedure

The user explicitly requested killing VRAM hogs before tests. Inspect nvidia-smi and ollama ps, unload resident models, identify and stop idle competing inference processes, then record the new memory baseline. Stop only identified expendable workloads; preserve active work. Run one inference workload at a time and unload it afterward, including failed runs. Repeat inspection before each test session.

### 2.3 [GH][VRAM] `--prefill auto` is capped at 8192 by construction, and the planner cannot search upward

**#4683**, created **2026-10-30T07:10:56Z**, 0 comments, open. RTX 3090 24 GB, Ubuntu 25.10, Qwen3.8-Flash-Next IQ3_S,
`--spec 4 --spec-min-p 0.5`, only `--prefill` varying within each pair. Timings measured on **0.1.47**, code checked
against **v0.2.8** and *"unchanged in v0.2.8 source but has not been re-timed there"*.

| prompt | `--prefill auto` | `--prefill auto:32768` |
|---|---:|---:|
| ~117.7K tokens | **108-127 s** | **58-64 s** |
| ~58.6K tokens | **43-46 s** | **30-36 s** |

The mechanism is two lines: `prefill_auto_max = 8192` (`generate.cpp:706`) caps the auto value, and the host prefill
plan's search `for (int64_t c = chunk; c >= 512; c -= 256)` (`:8704`) only walks **down** from the VRAM pick - so
*"when no chunk fits and 'fewest passes win', the planner can never choose a larger chunk, even though a larger one
wins."* A second, minor finding: `on_rotational_disk` (`:1431`) returns -1 on **btrfs** (anonymous `st_dev`, no
`/sys/dev/block` entry), so `drive_read_gbps` falls back to an assumed **1.5 GB/s** where the same NVMe measures
**~4.2 GB/s** - a plan price, not a truth.

**Why this reconciles rather than contradicts our record.** Our 2026-10-27 finding was that *"the engine's own chunk
beats a declared 4096 by +7.7 / +8.1 / +8.3 % prefill"* at a **19,769-token** prompt. Both statements are the same
mechanism: below the cap, auto picks **8192**, which is bigger than a declared 4096, so auto wins; above the cap it
cannot grow, so a declared 32768 wins by ~2x. **The chunk optimum is a function of prompt length, and a rung that does
not name its prompt length is unreadable.**

**Applies:** yes, directly - our ladder's 19,769-token prompt is in the regime where auto is right, and any long-context
row is in the regime where it is wrong. **Instrument:** the chunk ladder, with prompt length as a declared axis.
**Cost:** an edit now; a >=100K prompt arm is a run and needs the bump.

### 2.4 [GH][VRAM] A Windows layer-major prefill crash on long prompts, with a static root cause and a switch that avoids it

**#4695**, created **2026-10-30T10:22:33Z**, 0 comments. **Windows 11 (NTFS)**, RTX 5090 32 GB + RTX 4090 24 GB,
64 GB RAM, **0.2.7.1 / engine 0.1.52**, Qwen3.8-Flash-Next Coder IQ1_M, 131K, dual CUDA layer split, MTP, KV int8.

```
[strata] the engine reported an error: prefill (layer-major): expert source has no blob
[strata] the engine had stopped (exit code 1); starting it again (a minute or two) ...
```

The reporter's static chain: `src.drop_mapping()` at `generate.cpp:9204` sets `unmapped_ = true` to stop NTFS serialising

`blob_stable()` and fails. **`STRATA_PREFILL_LAYER_MAJOR=0`** routes long prompts through chunked prefill and avoids it,
losing layer-major prefill throughput.

**Applies:** as a hazard class on our platform, not as a defect we have - it needs a layer split, and we run one card.
But layer-major prefill is a **default in the 0.2.7/0.2.8 family**, and the failure is a **startup-class abort triggered
by prompt length** on the streaming path we rely on. **Instrument:** the gate already treats a start failure as void;
this adds a name to look for in the log. **Cost:** a line in the declaration.

### 3.1 [GH][VRAM] SLRU at one token of slots: 0.6 % hits, 32 % slower decode, and the fix was closed unmerged

**#31421**, created **2026-10-30T12:56:55Z**, 0 comments, `bug-unconfirmed`. Two builds on one box - Homebrew
**0.8.0 (build 11960, commit 8642541b2)** and a locally built LRU baseline **0.7.0-dev (build 11735, commit
098ce526b)**; Apple M3 Max 48 GB, Metal; `ggml-org/gemma-4-26B-A4B-it-GGUF` Q4_0 (**30 MoE layers, 128 experts,
top-8**); **200 prompts with a warm cache**; *"all runs generated the same 53,284 tokens"*.

| slots per layer | LRU `098ce526` | SLRU `8642541b2` (v0.8.0) | SLRU + protected cap |
|---|---|---|---|
| **8 (769 MiB)** = one token's experts | **37.5 % hit, 12.9 tok/s** | **0.6 % hit, 8.8 tok/s** | **37.5 % hit, 12.9 tok/s** |
| 16 (1,535 MiB) | 51.3 % hit, 15.0 tok/s | **53.6 % hit, 15.8 tok/s** | not run |

Log lines, verbatim: `hits = 77136, misses = 12784415, hit rate = 0.60 %, uploaded = 40787777.15 MiB` against
`hits = 4819191, misses = 8042360, hit rate = 37.47 %` at the same 240 slots. The proposed reading of
`touch()`/`victim()` is arithmetic: *"the 120-slot probation half is shared across all 30 layers and is smaller than the
240 experts one token needs. So misses from other layers evict a layer's experts before the next token can reuse them."*
The reporter's four-line patch caps the protected half at `min(n_slots/2, n_slots - n_expert_used * n_layers)` and gives
**hit and miss counts identical to LRU** at 1.0x, current SLRU at 2.0x.

**First bad commit is named:** `33d6135cb` = **#30637**, the LRU -> 50/50 SLRU change that landed **b11732**.

**Two consequences, and the first corrects our own record:**

1. **`v0.8.0` is past SLRU but is not a safe target for the low rungs of our ladder.** Yesterday's file said v0.8.0 is
   *"the first stable point past SLRU"* and implied the ladder could be re-run there. It can be re-run, but **the curve
   changes shape at exactly the rung that matters**: our knee was measured between 512 and 1024 MiB on LRU, and 769 MiB
   is where SLRU reads **0.6 %**. So the ladder must be re-run **and** the result must be read as a *different policy's*
   curve, with `-nr` and the slot count logged per rung.
2. **The fix we recorded as landed is not in any build.** **#30848** corrected this and was **closed 2026-10-27 without

## 4. Ollama - the error string we hit in October now has a cause, and it is a silent fallback

### 4.1 [GH][VRAM] `cudaHostAlloc` fails, ggml degrades silently, the next kernel launch dies with 303

**#17380**, opened **2026-07-24T21:10:49Z**, updated **2026-10-29T19:40:14Z**, 8 comments, open. Windows, CUDA,
**RTX 5070 Ti**, compute capability **12.0**, `cuda_v13` runner, `ARCHS = 750,800,860,890,1000,1200`; gpt-oss:20b.
Roughly **50 % of loads** fail during warmup:

```
ggml_cuda_compute_forward: MUL_MAT failed
CUDA error: shared object initialization failed
ggml-cuda.cu:106: CUDA error
  current device: 0, in function ggml_cuda_compute_forward at ggml-cuda.cu:2360
```

followed by `exit status 0xc0000409` (**STATUS_STACK_BUFFER_OVERRUN**). Identical flags succeed and fail *"sometimes 40
seconds apart"*. The correlation is a single line in the load log:

```
failing:    load_tensors:   CPU model buffer size =  1104.61 MiB
succeeding: load_tensors:   CUDA_Host model buffer size =  1104.61 MiB
```

The 1104.61 MiB buffer is the token-embedding table: `201,088 vocab x 2,880 embd x 2 bytes (bf16) = 1,158,266,880
bytes`. It stays host-side even with all layers offloaded, and **because Ollama forces `--no-mmap` on Windows+CUDA**
(`disabling mmap for llama-server load by default`, reason `windows_cuda`) that ~1.1 GB **contiguous pinned** allocation
is made fresh on **every** load, which is why the failure is easy to hit. The reporter's two findings, in his order:
*"the unpinned fallback path appears to be broken ... falling back to a regular host buffer should be a performance
degradation, not a crash"*, and *"the fallback is silent"* - even at `--log-verbosity 4` nothing says `cudaHostAlloc`
failed.

Confirmed pairs from one session, which is the evidence that makes this a mechanism rather than a guess:

| time | host buffer | result |
|---|---|---|
| 08:19:59 | `CPU` | **crash** |
| 08:25:49 (llama3.2:1b) | `CUDA_Host` | ok |
| 08:40:21 | `CPU` | **crash** |
| 08:41:02 | `CUDA_Host` | ok |
| 08:56:48 -> 08:57:39, six consecutive loads | `CUDA_Host` | ok x6 |

The workarounds are all host-side, which is what makes them ours: **pagefile from ~6 GiB free to ~77 GiB**; **reboot and
free host RAM**, *"which defragments the physical memory pool, which is what the ~1.1 GB contiguous pinned allocation
actually needs"* (free RAM at load 12.6 -> 20.4 GiB); and a faster model store (not causal). A second reporter
(yann-afx, 2026-09-01) adds a deterministic repro on an **RTX 3060 Ti (sm_86)** with the same `0xc0000409` + 303
signature, which takes it off the sm_120-only pile.

**Why this is a correction to our own record.** On **2026-10-11** we recorded `CUDA error: shared object initialization
failed` on the community `hob-b11434` build and attributed it to flash-attention shared memory, fixing it with
`-b 512 -ub 512`. That fix is real for that build (`launch_fattn` asking for more shared memory than the card allows),
but there is now a **second, incompatible cause for the same string on the same platform**, and it is a *pinned
allocation failure*, not shared memory. `0xC0000409` is also the code our 2026-10-27 note recorded from the Strata engine
(#1607). So the signature pair is not diagnostic by itself, and the `CUDA_Host` vs `CPU` line is.

**Applies:** directly - Windows, CUDA, sm_120 class, a pinned host buffer, and the commit/pagefile/fragmentation
variables our memory gate already reads. **Instrument:** the memory gate, plus one new field: **the host-buffer type in
`load_tensors`**. **Cost:** an edit; a re-run of the 2026-10-11 load is a start.

## 6. Colibri - no release for 24 days, and a 16-byte buffer that silently truncates output

### 6.1 [GH][ENGINE] Cyrillic comes out with U+FFFD because token bytes past 16 are dropped

**#2492**, created **2026-10-29T22:55:19Z**, open, **confirmed fix by the reporter**. Colibri **v2.0.0** (official
release), **Qwen3.6 engine (`c/qwen36.c`)**, model repo `Kreuzzelg/qwen36-35b-a3b-colibri-i4-gs64`, INT4 group 64, CPU
backend, Ubuntu Studio 26.04, Ryzen 7 5800U, **16 GB RAM**, model 23.0 GB in 41 shards, **1.3-1.5 tok/s**.

A Russian prompt returns corrupted words containing **U+FFFD**, in `coli chat` and through
`POST /v1/chat/completions` with `temp 0, stream false`, and it survives `COLI_LOOKUP=0`, `COLI_DENSE_IDOT=0` and
`QWEN_EXPERT_KERNEL=0`. The tokenizer was verified independently with the Hugging Face `tokenizers` library: the same
phrases round-trip cleanly, and several **token entries exceed 16 bytes** - ` экскурсии` 19 B, ` фотографии` 21 B,
` удовольствием` 27 B, ` впечатления` 23 B, ` путешествие` 23 B.

The cause is four lines of `utf8_drain()` at `c/qwen36.c#L539-L555`:

```c
for (int k=0;k<n;k++){
    if (*bn < 16)
        buf[(*bn)++] = b[k];
}
```

The function appends bytes from the whole token **before** draining completed characters, so **any token byte past the
16-byte buffer is silently discarded**. Moving the drain loop inside the input loop fixes it; the reporter rebuilt with
`make qwen36` and the same prompt returns clean Cyrillic, with *"no model weights, quantization parameters, or memory
settings changed"*.

**Applies:** as a correctness class rather than a defect we have - we have not run Colibri's qwen36 *text* path (our
Colibri work was Laya/decision models). But it is the third instance this month of the same shape: **a fixed-size buffer
truncating token text and producing output that reads almost correctly** - with #31102's 260-character Windows path,
#4304's five-token short reads, and now this. It is also another case where **Russian prose is the probe** (`#4603`
measured drafter acceptance on Russian prose at 61.8 % two days ago). **Instrument:** the text-identity check
(`ledger2`'s byte comparison), which would catch U+FFFD immediately. **Cost:** none, if the row ever runs.

### 9.2 [ARX][ENGINE] 2610.38981 - why speculative decoding beats its own prediction on fine-grained MoE

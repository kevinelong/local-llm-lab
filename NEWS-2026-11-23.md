## 3. [GH] The 0.1.66 decode regression has a second cause, and it is the **host layer**, not a kernel - which makes it reachable without a bump

Two reports landed in-window that separate the engine from the launcher, and one of them is a single-variable
A/B in the shape this lab insists on.

**`#6836`** (2026-11-23T12:45:14Z): 8 GB Blackwell laptop GPU, same server code (0.2.16), same model, same
arguments, **only `strata.exe` swapped**, three short coding controls plus a fresh ~120K-token retrieval,
temperature 0, seed 42, unique nonce.

| engine | expert slots | VRAM free | control decode | 120K retrieval decode | retrieval prefill |
|---|---|---|---|---|---|
| 0.1.62 | **886** | 336 MiB | **72.6 t/s** | 64.3 t/s | 969 tok/s |
| 0.1.66 | **562** | 740 MiB | **59.3 t/s** (-18.3 %) | 55.2 t/s (-14.2 %) | 953 tok/s (-1.7 %) |

The mechanism is in the startup arithmetic: 0.1.62 reserved **256 MiB** for "what is allocated after the
cache"; 0.1.66 reserves **384 MiB** in the first line and then demands **602 MiB** in the shrink line, so on
an 8 GB card resident experts fall **886 -> 562 (-36.6 %)** and decode tracks residency. **Forcing the
experts back does not help** - `--expert-cache 886` gives 918 slots, 250 MiB free, and **42.7 t/s**, *below*
0.1.66's own auto. The reporter's own conclusion is the useful one: 0.1.66 genuinely needs the extra
headroom, so the lever is `--vram-reserve-mib`, not the slot count.

The comment that matters to us (`real4root`, 2026-11-23T12:53:23Z) is **2x 12 GB, layer split, Windows
WDDM, driver 617.42, UD-Q4_K_XL, MTP, `--kv int8`** - our model family and our OS:

| engine | expert slots (both cards) | decode cache hit | standard-v1 decode short / 4K / 16K | prompt 16K |
|---|---|---|---|---|
| 0.1.52 | 1662 | **93-95 %** | **79.7 / 70.1 / 73.5** | 923 |
| 0.1.63 | 2358 | 50-79 % | 40.0 / 46.9 (best tuning) | 1028 |
| 0.1.66 | ~3620 | 56-64 % | 38.7 / 39.9 / 40.5 | **1093** |

**2.2x the slots, half the hit rate, and -43 % to -51 % of decode against 0.1.52**; prefill is the only thing
that improved. His diagnosis: *"the prompt path borrows 1348 of 1513 slots on the second card, and tiny
expert cache dampening (96 -> 32 swaps) kicks in … the hot set is not refilled after a prompt loan."* That
is the same quantity the 11-21 file made mandatory (`#6478`'s hit rate) coming back with a different cause.

**`#6846`** (2026-11-23T13:27:42Z) is the one we can act on **without any Strata download**: RTX 5060 Ti
16 GB (sm_120), 96 GB RAM, `qwen3.8-flash-next-iq2_xs`, `--max-context 8192 --kv int8 --kv-resident 8192
--spec 4 --mtp ... --expert-cache auto --vram-reserve-mib 1472`.

| Terminal code | Engine | Decode |
|---|---|---|
| 0.2.16 (+4 commits) | 0.1.56 | **89-90 tok/s** |
| 0.2.20 | **0.1.56 (same binary)** | 72-74 tok/s |
| 0.2.19 | 0.1.65 | 77-80 |
| 0.2.20 | 0.1.66 | 69 (72-74 with `--vram-reserve-mib 768`) |

With the new Terminal code **and the old engine**, every start logs a line that did not exist before:

```
strata serve: #4870 mid-coverage expert cache (6229 of 24576 slots, 25.3%): adaptive defaults every 4 -> 2, swaps 96 -> 192, decay 0.70 -> 0.92
```

So **`#4870`'s adaptive defaults cost ~20 % on a mid-coverage 16 GB card, and they live in `serve/`, i.e. the
app**, which is the second time this month a host-layer change has moved a number the engine did not
(11-20's `#6380` returned `reused: 0` from the same layer). A reply adds the 5080 datapoint: 140-150 tok/s
in the good days, **102.3 chat / 105.6 agent** now.

**Applies here?** The `#4870` line applies to **any** 0.2.19+ app on any engine; our rows are 0.1.47 and
predate it, and the readback is already in the declaration list from 11-21. The post-cache drop applies at
0.1.66. **Test:** the `chunk_ladder.py` gate already voids an arm whose granted cache differs from a declared
one - add "post-cache headroom" and the `#4870` line to the fields it reads, then one arm at 900 vs 1536
MiB reserve. **Cost:** an edit plus one start.

## 5. [GH] The DSpark drafter - the 402 MB file this lab shortlisted yesterday - **cannot start in either engine**, and the file itself explains why

Yesterday's shortlist item 6 was *"a 402 MB drafter we have never tried"*
(`dspark-Inkling-2-Mini-Q8_0.gguf`, 402,278,560 B). Both engines now have a measured reason to refuse it, and
they are different reasons.

**In Strata:** **`#6852`** (2026-11-23T14:14:11Z) - `strata-inkling` **0.1.66**, RTX 4070 Ti 12 GB, 63.8 GB
RAM, `unsloth` UD-Q4_K_XL:

```
[InkCUDA] Loaded .../Inkling-2-Mini-UD-Q4_K_XL.gguf (GGUF-NVFP4, fmt=gguf): trunk=3.93 GB (1.27s), experts=1202 GPU0 + 0 GPU-1 / 1870 host (72.24s ...)
[InkCUDA] Auto Host KV Offload (kv_fmt=0, 1.64 GiB free VRAM): global KV = 1280 VRAM + 2816 mapped host tokens (88.0 MiB host RAM, max_ctx=4096)
strata-inkling: missing tensor 'dspark.layers.0.self_attn.o_proj.weight'
```

exit **2**, both with `--dspark <file>` and **with no flag at all** if the file merely sits beside the model.
The same 54 drafter tensors converted to **safetensors** load and serve, so the weights are fine and the GGUF
name mapping is not. A Chinese-language report of the same failure (**`#6834`**, 12:24:14Z) says the
auto-provisioner *downloads* that exact file when a Q4_K_M Inkling model is chosen, so the failure is on a
path users reach by asking for the model.

**In llama.cpp:** the reason is upstream of both engines, and it is in the pack's own
`dspark/README.md` (read today). The two Unsloth-format drafters have **54 tensors and
`general.architecture = dflash`**, and *"Mainline llama.cpp has no DSpark support yet; it is open as #32218"*,
whose head reads a **newer** drafter format (unpadded `markov_w1` [256, 200058], an explicit `markov_w2`,
softmax-normalised `ctx_mix`). Mainline needs the `.gguf_file` variants shipped beside the models, *"use the
Unsloth llama.cpp prebuilt (unslothai/llama.cpp releases), which carries looped-layer support and the DSpark
drafter as pins"*, and `--spec-draft-n-max` is clamped to **7** because the trained block size is 8. The
README also states Q8_0 accepts drafts at the same rate as BF16 in their tests, with a worst relative RMSE
of **0.62 %** on the 27 attention/MLP projections.

**Consequence:** yesterday's item is **struck, not postponed**. A `--spec-type draft-dspark` row needs
Unsloth's fork build, which is a different engine and a second variable; the Strata path needs a fix that
does not exist. **Cost of finding out was zero** - the pack's README and one issue did it.

  12 GB card**, which is why `moe-cache-tune.py` reported `no room on CUDA0 for a cache larger than 1472

  overflow go to shared GPU memory, so it does not crash - it just leaves no cache.
- **The cache counts the looped layers three times**: `CUDA0 MoE cache size = 7288.58 MiB for 28188.00 MiB
  of host experts` against a **15,066 MiB** expert file. The patch gives layers that share a weight one
  slot owner (`src/llama-moe-cache.cpp`, `LLAMA_MOE_CACHE_SHARE=1`): hit **81.5 -> 94.8 %**, decode

  caches still prefer 0.95. This contradicts the "share 0.95 is always right" reading of the 11-16 video -
  and it is the same "the sign depends on the cache" rule we already hold, one step further.

  after the patch with share 0. **With the CPU share on, all three diverge even between unpatched arms.**

  loop-layer experts on the CPU that path corrupts; **`--no-op-offload` fixed all six broken configurations**.

  intervention over layers and decoding steps finds the prompt-span redundancy *"is about form rather than
  content"*, and replacing it works only in specific ranges - the measured version of "the prompt cache is

- **`DPMA: Learning to Compress Mixture-of-Experts Models`** (cs.LG) - prune, merge and *absorb* jointly with

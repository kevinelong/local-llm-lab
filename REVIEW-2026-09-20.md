Research window: September 14-20, 2026, through this review. Focus: Windows, RTX 5070 12 GB, 32 GB RAM. This is research and an audit of saved programs, not a new model benchmark. Publisher measurements are explicitly separate from local evidence.

The authorized follow-up experiments are recorded separately in [RESULTS-2026-09-20.md](RESULTS-2026-09-20.md). Consult that report for executed evaluator, replay, Pi, and Bonsai results; the recommendations below preserve the review's original rationale.

### Bonsai feasibility

The card lists PTQ1_0 at 5.95 GB and PQ2_0 at 7.21 GB, with PQ2_0 favored on tested Blackwell hardware. Both require Prism's llama.cpp fork; stock loaders are unsuitable. These are weight sizes, not total VRAM. Start with text only and 8k context, then measure 16k. There is no verified RTX 5070 result here. [Model card](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf).

Prism's demo provides Windows PowerShell launchers and Windows CUDA build/download paths. Verify the selected binary supports this GPU. Pin the fork commit, weight revision, packing, and chat template together. [Runtime guide](https://github.com/PrismML-Eng/Bonsai-demo).

The launch announcement and current card report different benchmark suites and throughput figures. Do not combine their numbers into one reproducible result or equate aggregate retention with success on our tasks. [Announcement](https://prismml.com/news/prismml-launches-bonsai-2-27b), [card](https://huggingface.co/prism-ml/Ternary-Bonsai-2-27B-gguf).

Maple-Preview is an older CPU research candidate newly supported in the stable llama.cpp release. Its publisher explicitly describes limited agentic post-training. Prioritize it for CPU reasoning/extraction before autonomous coding; Apple speed claims do not predict our Intel CPU. [Publisher card](https://huggingface.co/deepgrove/maple-preview), [runtime release](https://github.com/ggml-org/llama.cpp/releases/tag/v0.4.1).

## What the prior work actually establishes

- The September 16 captured request exceeded its 4,096-token output allowance. An 8,192-token replay completed, using 8,101 output tokens. This controlled replay is strong evidence for that request, not every historical streaming failure.
- A fresh 8k-output agent run still failed. The 32k-context/12k-output trial delivered 115/115 terminal signals but only 2/10 historical and 0/4 supplemental program checks. Transport and program correctness must remain separate.
- Smaller repairs worked: Qwen passed all three graph trials, Omni passed two graph trials and all three interval trials, and Smoffyy passed all three interval trials. Omni's other graph evaluation timed out. These results contradict a broad claim that local models cannot handle graph algorithms.
- The conventional CPU baseline is real: Smoffyy ran with no model VRAM allocation. The repeated thread sweep gave medians 9.97, 11.71, 11.99, and 11.63 output tokens/sec at 4, 8, 16, and 24 threads. This supports a plateau for that workload, not a universal 16-thread optimum.
- The September 15 runs changed multiple settings during debugging. They measure complete configurations; they cannot isolate the effects of model, thinking, compaction, or harness independently.

The Aider cycle diagnosis in HARD-SPEC-TEST.md is wrong. The program implements the edge command and cycle detection. Reproduction prints `cycle detected: [1, 2]` but exits 0 because the `plan` command catches `SystemExit` and discards it. This is an exit-status bug, not evidence that the model failed to implement the graph algorithm. It also fails never-reused IDs and the combined successful-self-test/data-preservation check.

Claude's program fails the supplemental self-test preservation check. Its `load(path=DATA_FILE)` and `save(state, path=DATA_FILE)` bind their defaults when defined; subsequently changing the global in the self-test does not redirect those defaults. A focused reproduction confirmed that `test` exits 0 and prints success while replacing the existing PRESERVE_ME task with its test fixtures. See the saved before/after contents and command output. A clean 10/10 did not establish all-spec correctness.

A deliberately crashing control program earned 1/10: the invalid-dependency test accepts any nonzero exit without requiring successful setup or checking the diagnostic. This confirms the known false-positive risk rather than merely hypothesizing it.

The historical scorer also does not check CSV content after round-trip, forced-deletion edge cleanup, most argument validation, search, block, graph, or full ready/stats behavior. Passing its self-test check means exit 0, not that the requested assertions ran. The supplemental checks improve coverage but still do not cover the full specification.

## Assumptions to revise

| Old assumption | Supported replacement |
|---|---|
| Local 8/10 demonstrates an algorithmic ceiling | One configuration failed two checks on one task. The cycle explanation was incorrect, and broader capability remains unmeasured. |
| All frontier outputs were fully correct | They passed the historical ten checks. Claude's saved artifact fails a later preservation check. |
| Dense near-30B is always impractical on 12 GB | Muse-Glimmer's tested configuration was slow. Packed ternary models and new kernels warrant a new experiment; usable memory and speed are measured properties. |
| Active parameter count entirely explains offload speed | Weight representation, memory traffic, kernels, context, prefill, and host/GPU transfer behavior also matter. Existing cross-model comparisons do not isolate one cause. |
| Temperature zero makes results reproducible | It reduces sampling variation. Preserve runtime/weights/prompts and repeat for operational stability; repeat runs are not independent task diversity. |
| Always enable or always disable thinking | Test explicit operating modes under stated time/output budgets and verify actual wire behavior. The old bat-and-ball probe cannot determine the best coding policy. |
| More context fixes long writes | Input capacity and output allowance are distinct. Compaction reserve must leave adequate response headroom. |
| OpenCode is unusable on local Ollama | RESULTS.md contradicts its own successful smoke row. It worked for some configurations; the later hard-task configuration performed poorly. |
| High decode tokens/sec means a useful coding agent | Report end-to-end verified success, prefill, first-token latency, repairs, total tokens, and time. Tokenization also differs between models. |

## Proposed next experiments, in order

1. Create evaluator v2 while freezing the historical scorer. Require successful setup; distinguish expected rejection from crash/timeout; validate persisted CSV and dependency state; test all commands and self-test isolation. Keep historical and v2 scores separate. Validate with known-correct implementations and intentionally broken cases.
2. Replay the captured failing request on the currently installed Ollama 0.34.2 at fixed 4k/8k/12k output limits. Record the same request/weights and wire events. If 0.34.0 is not available, compare to the saved trace and label this a historical comparison, not a simultaneous A/B.
3. Compare Pi 0.85.1 and an isolated 0.86.1 using the same backend, weights, prompt, adequate output reserve, and time limit. Inspect strict-schema negotiation and actual thinking controls. Turn off cache warming for the experiment so idle inference does not confound timing.
4. Add Bonsai 2 with its required runtime. First pass text, tool-call, and streaming controls; then small repairs and the full task. Compare PQ2_0 versus PTQ1_0 only after one works. This changes model and runtime together: label the result as a deployment comparison. Use the same conventional GGUF on both runtimes where supported to estimate runtime effects separately.
5. Compare full-spec prompting against explicit staged implementation using fixed model/runtime and total budgets. Use at least five distinct tasks and three fresh workspaces each for promising setups. Report task-level success and uncertainty; do not count 55 checks as 55 independent tasks.
6. Revisit specialized CPU models separately. Keep transcription and retrieval as independent tracks with their own quality measures.

Continue one inference workload at a time, inspect and free expendable model VRAM first, and unload after each trial. Preserve raw requests, model hashes, evaluator revision, sampling parameters, token limits, compaction settings, elapsed time, errors, first artifact, and final artifact. Do not select winners on partial score alone.

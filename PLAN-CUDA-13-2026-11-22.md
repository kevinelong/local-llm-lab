## Why

`D:/tools/cuda-12.9` was assembled from `redistrib_12.9.1.json` (nvcc 12.9.86, cudart 12.9.79, cccl 12.9.27,
cublas 12.9.1.4, nvml headers 12.9.79). The published line is now **13.5.0**, and `12.9.2` exists beside it. The
only plausible gain on this box is newer **cuBLAS** heuristics for prefill and a newer **ptxas** for the same
`sm_120`; everything else in the release notes (new architectures, cuDNN/cuSPARSE, multi-GPU) does not touch this
path. So the job is not "upgrade", it is **measure 12.9 against 13.5.0 with identical flags and keep the winner**.

## Steps

1. **Gates** (unchanged, do not lower): >= 9 GiB free physical, >= 8 GiB commit headroom, WSL `Stopped`,
   no `llama-*` process, GPU idle. Record the numbers beside the result.
2. **Fetch the manifest, then only the components used before**, and verify every sha256 against it:
   `cuda_nvcc`, `cuda_cudart`, `cuda_cccl`, `libcublas`, `cuda_nvml_dev` - plus `libnvjitlink` if cublas in 13.x
   demands it (it is what a newer cuBLASLt links against; add only if the build asks).
   `https://developer.download.nvidia.com/compute/cuda/redist/redistrib_13.5.0.json`
3. **Extract to a second tree**: `D:/tools/cuda-13.5` (each archive has one top directory; strip it and merge).
   **Do not touch `D:/tools/cuda-12.9`** - it is the measured baseline and the only toolchain with numbers.
4. **Configure a second build directory**, so the 12.9 binaries survive: `build-cuda135` in
   `D:/build/llamacpp-b12611`, Ninja + `cl` from `vcvars64.bat`,
   `-DCMAKE_CUDA_COMPILER=D:/tools/cuda-13.5/bin/nvcc.exe -DCUDAToolkit_ROOT=D:/tools/cuda-13.5`,
   `-DCMAKE_CUDA_ARCHITECTURES=120 -DGGML_NATIVE=ON -DLLAMA_CURL=OFF`.
   The Visual Studio generator still cannot be used (no CUDA toolset integration).
5. **Build** `llama-cli llama-server llama-mtmd-cli`, same targets as before.
6. **Measure the same four numbers** with the same prompts and flags, both ctx sizes, `-n 32`, `-ub 512 -fa on`,
   `-ngl 99`; then one 32K server run for VRAM resident. Same picture for the vision check.
7. **Compare and decide.** Adopt 13.5.0 only if prompt or generation improves beyond noise (about 3 %) at equal or
   lower VRAM, or if the 13.5 build loads where 12.9 failed. Otherwise keep 12.9 and say so; a version number is not
   a result.
8. **If adopted**: point `D:/build/serve-inkling-32k.bat` at `build-cuda135/bin`, keep the 12.9 tree, and re-record
   every number in `INKLING-2-MINI-2026-11-21.md` as measured on 13.5.0 with the date.
9. **Either way**: append the outcome (both numbers, the verdict, the reason) to
   `INKLING-2-MINI-2026-11-21.md` and update the `AGENTS.md` headline. Do not delete the losing toolchain in the
   same session that measured it.

## Known traps, paid for already

- **Do not mix DLL sets.** Each build directory's `bin` ships its own `ggml-cuda.dll` and needs the matching
  `cudart64_*.dll`/`cublas64_*.dll` from its own toolkit on `PATH`. A 13.5 build run with the 12.9 bin first on
  `PATH` will fail with a DLL error, not a compile error.
- **`--no-warmup` hides the crash, unbuffered output shows it.** `llama-cli`/`llama-server` are fine; `mtmd-cli`
  needs the jinja fallback patch in `patches/` (already applied to this tree).
- **`-ub` default is 2048 and costs 45x** on `inkling2_loop`; every measurement must state `-ub 512`.
- **Thinking eats short budgets**: `/v1/chat/completions` needs `"reasoning_effort": "none"` for short answers.

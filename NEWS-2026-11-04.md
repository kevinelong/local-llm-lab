## 1. [GH][REL][ENGINE][VRAM] Strata: 0.2.10 / 0.1.56, and the two reasons not to take it blind

### 1.1 [REL][ENGINE] What 0.2.10 changes that reaches a Windows 12 GB card

`v0.2.10`, published **2026-11-02T23:52:47Z**, `prerelease: false`, **40 assets**, and the asset table confirms the
version split the body claims: `strata-control-0.1.56-windows-x86_64.zip` (73,292,001 B),
`strata-engine-0.1.56-windows-x86_64-cuda-cuda13.tar.gz` (**627,806,827 B**), `...-cuda-cuda12.tar.gz` (915,332,848 B),
`strata-dsv41-0.1.56-windows-x86_64-cuda-cuda13.tar.gz` (422,611,679 B). For scale, the same **cuda13 Windows** engine
was **580,428,476 B** at 0.1.47 and **581,368,579 B** at 0.1.50, so the package grew ~47 MB this release.

The items that reach this box, in the release's own words:

- **DFlash2 is the default drafter for Qwen3.8**, and the engine list is explicit: "CUDA cards of architecture **8.6,
  8.9, 12.0 and 12.1**, Radeon gfx1100, gfx1151 and gfx1201, Apple Metal, and Intel Arc." Our RTX 5070 is **compute
  capability 12.0**, so this is our card. "DFlash2 is small, about **0.7 GB** (the engine prints **625 MiB** of graphics
  memory with the Q4_0 selector), so the **5.2 GB MTP layer is not downloaded or loaded**. The first start downloads
  about **1.2 GB** (41.5 s on the test PC) and builds the drafter file on your computer."
- **One drafter per run, never two.** "The choices are Auto, MTP, DFlash2 and Off... Each loads exactly one drafter. A
  setting an older version saved that named both ('both', 'mtp+dflash2') now counts as Auto."
- **Auto picks MTP** when several requests run at once (`--parallel` or `--batch` of 2 or more), when no engine with
  DFlash2 is installed, for DeepSeek and the ISTA-DAS Coder, and **on the all-cards split engine**. "DFlash2 answers one
  request at a time. When you have not chosen a number of requests, the app now loads the model for one request at a
  time with DFlash2, on one card and on several (0.2.9 filled in up to 4 at once with MTP)."
- **The measured DFlash2-vs-MTP delta on sm_120 exists and is small.** The one sm_120 row is an **RTX PRO 5000 (CUDA,
  sm_120), IQ3_S: +7.88 % on greedy answers, +6.23 % on short sampled answers, +1.38 % on long ones (2K tokens)**. The
  larger rows are other hardware: Strix Halo on Windows UD-Q4_K_XL **+12.0 % short / +8.8 % long**, R9700 **+6.6 / +4.2**,
  DGX Spark **+5.8 %**, M5 Max **+7.4 % (UD-Q4_K_XL)**, **Intel Arc A750 2.6 % slower than MTP**. So the number our card
  can expect from the drafter change is **+1.4 to +7.9 %**, and **the release says greedy runs show larger gains than the
  sampled ones quoted**.
- **A Windows RTX 5070 12 GB validation line exists, and it is a checks list rather than a rate.** Under "What we ran on
  the release files": "**Windows PC with an RTX 5070 (12 GB):** the CUDA 13 and CUDA 12 packages passed these checks:
  **128K on Auto with DFlash2 alone**; two requests at 128K on the full card and squeezed to about 8 GB (the context
  stayed 131,072); MTP chosen loading only MTP; the GPU picture reader; Gyro-S on Auto; and a start limited to about
  8 GB." **No tokens per second on our card in this release.** The nearest same-card rate is a community benchmark
  (sec. 1.4).
- **128K context on 8 GB cards, and 12 GB cards are explicitly unchanged.** "**12 GB cards are unchanged.**" The
  short-of-memory walk is: KV window steps down (20,480 -> 8,192 -> 4,096), then the MTP layer is dropped, then the
  prompt path's buffers keep **16 expert-cache slots instead of 128**, and "as the last step, the output head (**0.41
  GiB**) sits in pinned host memory, which makes decode about **3 times slower**." That last step is the one that has a
  named defect (sec. 1.6).
- **The all-cards split engine is Linux-only on Auto and is not ours.** Its Auto conditions are: Linux; exactly two NVIDIA
  cards of 8.6 or 12.0, or four R9700; a Qwen3.8 file; every routed expert in the cards' memory; ~43 GiB free RAM; and
  context <= 131,072. "We ran it on two RTX A6000, two RTX PRO 6000 Blackwell and four R9700 cards, **not on a GeForce
  pair**." The desktop app "keeps the layer split with DFlash2 and gets the split engine in 0.2.10.1."
- **Rollback is one command and does not move Control:** "`strata components rollback` returns to the **0.1.55** engine;
  Control stays **0.1.56**." And for the drafter: "`strata launch --drafting mtp`."
- **A CUDA-12 first-start cost worth knowing before any A/B:** "The CUDA 13 package starts in about a minute on an RTX 50
  card (60 to 80 s measured). The **CUDA 12** package... builds its GPU code on the first start: **310 s** measured on a
  Blackwell card (compute capability 12.0)."

### 1.2 [GH][ENGINE] Two mechanisms make 0.1.56 slower than 0.1.54, and only one is visible in the slot count

**#5115** (created 2026-11-03T13:35:44Z, updated 2026-11-04T09:31:37Z, open, 1 comment) is the closest thing to our own
row: **Windows 11, RTX 5080 16 GB (sm_120), driver 621.01, Ryzen 9 9950X, 2x32 GB DDR5-6400**. Engines 0.1.54 (source
`f-028-rel`, commit `8c1aea4bca1b`) and 0.1.56 (source `f-0291-rc1`, commit `06698c674673`), "both archs `[75,86,89,120]`,
CUDA 13.0" - **which is the reporter's evidence that the 0.1.56 Windows package still carries sm_120.** Model
Qwen3.8-Flash-Next GSQ-RCO **IQ3_S**, identical arguments in both arms, **only the engine binary changing**.

| arm | engine | expert slots | VRAM free after load | decode median | 60K read |
|---|---|---|---|---|---|
| 1 | 0.1.54 | 3083 | 921 MiB | **117.0** | 3207 |
| 2 | 0.1.56 | 3104 | 874 MiB | **86.1** | 2769 |
| 3 | 0.1.56 | 3062 | 922 MiB | **84.9** | 2728 |
| 4 | 0.1.54 | 3185 | 976 MiB | **111.2** | 3150 |

Mirrored means **0.1.54 114.1 against 0.1.56 85.5 = -25.1 % decode, -13.5 % prompt read**; within-condition spread
**5.0 %** and **1.4 %**, ranges non-overlapping; GPU 47-53 C, 2872-2887 MHz, no throttle reason in any arm. Two earlier
runs on driver 617.42 and a worse PCIe state gave **-30.4 %** and **-22.4 %**. Two declared limits that matter to us:
**DFlash2 was not tested** ("`--draft dflash2` needs a drafter pack that the app builds on its first start (about 1.2 GB
download); the manual server path in this setup does not provide it"), and turning the prompt lookup off
(`--lookup-max-t 0`) gives 0.1.56 back **+11.5 %** but leaves it ~25 % behind.

**#5199** (2026-11-04T09:31:26Z, open, 0 comments) supplies the second mechanism, **on the DeepSeek path** (`ds4:` log

the chunk changing; the free figure is the tell:

```

   CUDA0 ... experts 5.95 GB (572 of 15360 in VRAM), 379 MiB free
0.1.56, default:      ds4: ... prompts in chunks of 16384
   CUDA0 ... experts 2.89 GB (258 of 15360 in VRAM), 947 MiB free
0.1.56, chunk 8192:   ds4: ... prompts in chunks of 8192
   CUDA0 ... experts 7.25 GB (707 of 15360 in VRAM), 403 MiB free
```

| arm | engine | chunk | slots | 4K prompt | 16K prompt | short decode | long decode |
|---|---|---|---|---|---|---|---|
| 1 | 0.1.55 | 4096 (default) | **572** | 348 | 767 | 14.83 | 12.11 |
| 2 | 0.1.56 | 16384 (default) | **258** | 325 | 786 | 12.68 | 10.82 |
| 3 | 0.1.56 | 4096 | 707 | 303 | 657 | 14.52 | 11.94 |
| 4 | 0.1.56 | **8192** | **707** | 344 | **805** | 14.43 | 12.05 |
| 5 (control) | **0.1.55** | **16384** by hand | **240** | - | - | - | - |

Arm 5 is the control that makes this a chunk measurement rather than a code-change measurement: **0.1.55 with 16384
given by hand also falls to 240 slots.** The reporter's reading of the path - "the prompt path lends VRAM from a device's
layers and keeps its last `tail_k` slots in one buffer (`Chunk::borrow`), and the chunk rule is picked before the expert

our own #4261 line prints ("`prompt chunk N, not M ... an 8192-token chunk borrows N of them`", `NEWS-2026-10-27`).
**The one number to carry: 0.1.56's default leaves 947 MiB unused instead of filling it with expert slots, i.e. the room
is taken by the prompt path's loan, not by a real cache allocation.**

**#5115's own comment (MingShi350, 2026-11-04T09:31:37Z) is the correct synthesis and I am quoting it because it is the
bump's shape**: "on that card the 0.1.56 loss is visible in the slot count itself, whereas your report shows the same kind
of loss with the slot count unchanged (3083 vs 3104). **Two different mechanisms, same release; fixing either one alone
will not bring 0.1.56 back to 0.1.54 here.**"

### 1.3 [GH][VRAM] The 0.2.10 app stops sending `--resident-budget-gib`, and a 64 GB Windows box cannot start

**#5059** (created 2026-11-03T05:47:48Z, updated 2026-11-04T10:01:11Z, open, **7 comments**) is the item that should
gate the bump for this machine, because its box is ours: **64 GB RAM, 16 GB VRAM, Windows 10.0.26300** (the same build
family as this workstation), and the model is IQ3_S with `--mtp` and `--expert-cache auto --prefill auto --spec 4
--spec-min-p 0.5`.

The finding is a single-flag regression between app versions with the **engine held fixed**: "Strata 0.2.10 / engine
0.1.56 (**fails**) - Strata 0.2.9 / engine 0.1.56 (**works**)". Both runs pin the engine through
`components\.updates\state.json` (`active` and `pinned` both `0.1.56-windows-x86_64-cuda-cuda13`, with `0.1.55` under
`previous`), so **the app is the only variable**. The two launch lines differ in one place: "**0.2.9 adds
`--resident-budget-gib 40`, 0.2.10 adds no RAM setting of its own and additionally removes the `--resident-budget-gib`
that was already in my run config.** Without that flag the engine takes a different path - a **20 s arena wait, the `mmap`
fallback, then a ~43 GiB page-locked copy** - and that is the run the app does not accept as started."

`[INFERENCE]` that 43 GiB page-locked copy is priced by a fact we already hold from three directions: **#4860's ~23 GiB
single-allocation ceiling inside a ~46 GiB NON_LOCAL pool** (`NEWS-2026-11-01`), the **17.8 GiB of WDDM `Shared Usage`** we
measured under one resident arm (`WDDM-SHARED-SEGMENT-2026-10-22.md`), and **Colibri's merged Windows commit-headroom
fix** (`NEWS-2026-11-02` sec. 3.2). A 43 GiB one-shot page-locked copy on Windows sits past the first and near the second.
**Not claimed as measured** - the reporter shows the launch lines and the failure, not the allocation trace.

Practical consequences, both cheap: a 0.2.10 bump on this box should **declare `resident_budget_gib` explicitly in the run
config** rather than rely on the app's default, and the app/engine pair should be moved together with a note of which one
carries the rollback (`strata components rollback` moves the engine to 0.1.55 and leaves Control at 0.1.56).

### 1.6 [GH][VRAM] DFlash2's confidence is priced without `--kv-resident`, and `--prefill-head-alias` fails deterministically

Two items from today, both flag interactions, both cheap to check before trusting a 0.2.10 number.

**#5213** (2026-11-04T13:00:43Z, open, 0 comments): on a single 32 GB R9700 with Qwen3.8-Flash-Next UD-Q4_K_XL,
`--max-context 163840 --kv-resident 32768`, an Auto/DFlash2 start "picks `--draft-conf 0.35`", while the engine's own log
says `expert cache 8312 slots` and "`drafting.CONF_STEPS` prescribes **0.5** for 7,500 to 12,000 slots". Measured, same
start otherwise, 3 rounds each, 1,000-token generation:

| `--draft-conf` | decode tok/s | draft acceptance |
|---|---|---|
| 0.35 (what the start picks) | 66.7 | 58.4 % |
| 0.5 (what 8,312 slots prescribe) | **71.1** | **67.0 %** |

"Against the MTP on the same build, 0.35 is about **-3.4 %** decode and 0.5 is **+8.2 %**." Cause as static analysis:
"`strata_control/drafting.py:505` `expected_slots()` reads `--max-context`, `--kv`, `--vram-reserve-mib` and `--prefill`,
but **not `--kv-resident`**... For this config that prices the KV session at **2,382 MiB instead of 792 MiB**, 1,590 MiB
too high, which is **815 slots**." **Our own ladder declarations all carry `--kv-resident 32768`**, so on this engine our
auto-picked drafter confidence would be mispriced in the conservative direction - and the reporter's own limit is that the
estimate is still high after the fix ("11,558 against the engine's 8,312"), so the correction is partial.

**#5188** (2026-11-04T07:05:17Z, open, 0 comments): with `--prefill-head-alias` on an RTX 4060 8 GB, "the engine starts and
answers the launcher's own first request (53 tokens). **The next request fails with HTTP 400**: `--prefill-head-alias: the
output head was reloaded at another address, so the captured verify graphs would read freed memory`", and in the start

### 4.1 [ARX][ENGINE] Bevy (2611.04794): prefetching can be *harmful* when there is an expert cache, and scheduling beats it

**"Accelerating Offloading-Based MoE Inference by Interleaving Concurrent Requests"** (2026-11-02). Verbatim: "Expert
offloading enables large mixture-of-experts (MoE) language models to run locally, but conventional batching stalls the GPU
while missing experts are fetched. A popular remedy, known as **prefetching**, is to predict what experts will be needed
soon and fetch them using idle link bandwidth. Imprecise prediction, however, wastes bandwidth and GPU memory on fetching
unnecessary experts. **Our key finding is that prefetching can be harmful when there is an expert cache in GPU memory.
This is because as the cache includes more necessary experts, expert prediction becomes less precise. Our key insight is
that proper request scheduling beats prefetching.** Building on this insight, we present **Bevy**, an MoE inference system
based on runahead inference for concurren..."

**Why this is item 5 of the headline and not a footnote:** our shortlist has carried **#4978 "routing-neutral residency:
the 12 GB card wants the prior's page-in saving without its routing change (prefetch-only / VRAM-tier pinning /
cost-aware `--resident-experts`)"** since 2026-11-02, and before that the **"warm/calibrated expert-cache seed"** from
`NEWS-2026-10-16` (the "6 % -> 42 % hit rate" claim). Both are prefetch-shaped, and both assume the cache and the predictor
improve together. **This paper's mechanism says they trade against each other**: the more of the needed set the cache
holds, the less precise prediction becomes, so the value of prefetch falls exactly as the cache gets good. It does not
refute either item; it predicts that each will show a smaller effect the larger the cache rung, which is a testable shape
and one our ladder design already produces (chunk/reserve at fixed rungs). **Note the regime limit: this is
offloading-with-concurrency, and our serving config is `--parallel 1`, so the paper's *scheduling* half has no lever
here - only the prefetch half applies.**

### 4.2 [ARX][VRAM] FlagRot (2611.03992): rotation does not always help a low-bit KV cache, and which axis you quantise decides

**"FlagRot: Selective Rotation for Low-Bit KV Caches"** (2026-11-02). Verbatim: "Long-context inference is bound by the KV
cache, which **2-bit codes could shrink about sixfold** if their error stays in check. The usual remedy rotates keys before
quantizing, **assuming rotation always helps. However, we observe that it does not: rotation flattens a spiky piece of a
key but can give a flat one a new peak, and both coexist within one key.** We therefore propose FlagRot, which stores each
**32-channel piece rotated or as is, whichever has the smaller calibrated attention error**, and rotates the query instead
when reading. We further show that **how often to decide follows the quantization axis: per-channel caches such as KIVI
need one decision per head, at no write cost, while per-token caches decide per key, with the choice stored in existing
sign bits**..."

**Why it reaches us:** rotation-before-quantisation is assumed by the quantisation schemes in our own KV work - our
untried **"convrot vs nvfp4 on weights already on disk"** item (`SHORTLIST-2026-10-26-untried.md`), and Strata's
`--kv k8v4` / `k8v4` axis from `NEWS-2026-10-25`. The paper's claim is narrow and cheap to test in principle: whether a
piece of the key benefits from rotation is **per-piece and decidable**, not global. Its own regime is 2-bit codes, and our
KV rows are int8 and k8v4, so **the finding is a caution about the *assumption*, not a measurement at our bit width.**

**72,117,786,752 B = 72.1 GB**, which is **exactly** the figure 0.2.10 publishes for the ISTA-DAS Coder ("five model
files in `IQ2_XXS/` (**72.1 GB**), the Engram file (110.6 GB) and the picture file (0.97 GB)"). So **Strata's built-in
`--model ISTA-DAS-Coder` takes shards 2-5 and ignores shard 1 and the absent shard 6**, and its own integrity check is
"every file is checked against its **pinned size and SHA-256**, and a stopped download resumes" - i.e. the app pins a
list that need not match the repo's shard numbering. **For us the practical rule is unchanged and now sharper: a re-stage
of this pack must go through the app's pin list, never through "download all files".** `[INFERENCE]` a shard set missing
`00006` is not loadable by a loader that reads the split header, so a hand-built download of this repo today is still
broken.

Also from 0.2.10 and worth recording because it prices the DeepSeek decision for the first time with a *first-class*
command: for someone with no DeepSeek file the Coder download is **191 GB** (72.1 GB model + 110.6 GB Engram + **8.0 GB
drafter**, which "the first launch of any DeepSeek set fetches... also with `--dspark off`"), and **80 GB** if an Engram
copy is already there. The Engram "stays on the SSD: the model reads a few of its rows for each word, so it is not counted

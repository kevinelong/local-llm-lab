### 2.1 [GH][VRAM] #4860: the 50 %-of-RAM folklore is a per-allocation ceiling; the pool is the DXGI non-local budget

Unmerged PR, **2026-10-31T22:31:46Z**, with its own measurements on *"a desktop RTX 3090 Ti + RTX 3090, 64 GiB RAM,
Win11 Home, CUDA 13"*. Two limits named, neither of which is the pool:

- *"A single pinned allocation caps at ~23 GiB regardless of free RAM or pool. Measured ... one-shot
  `cudaHostAlloc` and `cudaHostRegister` succeed at 23 GiB and fail at 24 GiB with 58 GiB RAM free - while cumulative

- *"Stock 0.1.55 at a 23.24 GiB complement logs `page-locking refused (out of memory); trying pageable memory` - silent

**Why this matters to us, concretely.** Our 2026-10-22 note derives a **~31.7 GiB `[INFERENCE]`** ceiling from

**pool** on a 64 GiB box is ~46 GiB, not ~32. So the note's ceiling is simultaneously **about right for one
`cudaHostAlloc`** and **about 14 GiB too low as a pool total** - and the failure mode at the limit is the one we have
recorded elsewhere: **silent degradation to pageable memory**, not an error. Note this is the third Windows item this
month whose failure is silent (#4808 yesterday, #4879 below, this one), and they are all the same shape.

**Also in it, and separately useful:** a measured copy-rate difference between pin modes -
**6.25 GB/s H2D registered against 4.29 GB/s `Mapped|Portable`** (*"measured 2026-10-24, engine 0.1.48 prototype"*) -
and a token-identity result: *"same binary with and without the env, temp 0, two captures per arm: 4/4 byte-identical;
plus 2/3 prompts byte-identical against the stock release build (the third varies across cold loads on ANY build -
speculative-decode timing, not the patch)"*. The pinned-vs-pageable copy microbench has been on this lab's shortlist
since 2026-10-24 as the cheapest open item; this is that measurement on someone else's hardware, and the ratio is 1.46x.

**Not claimed:** the patch's own limits are stated - *"Not run: full end-to-end load of a >23 GiB complement ... Linux/

### 2.4 [GH][VRAM] #4825: a Q6_K dequant produced non-finite values, and the router turned that into a GPU fault

Created **2026-10-31T17:22:34Z**, Ryzen AI Max+ 395, 128 GB, Linux, ROCm 7.15 in a container, Strata v0.2.9
(engine 0.1.55), dsv41 built for gfx1151, **unsloth DeepSeek-V4.1-Flash UD-IQ1_M**. Every prompt of **96 tokens or
more** (the chunked pass) aborts with a `moe_sort_kernel` memory fault; shorter prompts and `--prefill-chunk 0` work;
`DS4_YOCO=0`, `DS4_LAYER_MAJOR=0` and `STRATA_DENSE_PFGEMM=0` do not help.

The dumps are the value. On a 397-token prompt, layer 0: `attn_x nonfinite=0`, **`qr_raw nonfinite=452977` (about 90 %
of T x q_lora)**, `kvr_raw nonfinite=183414`. `wq_a` and `wkv` are **Q6_K** in that set, so the dense weights go through
`iq::dequant_rows`, which on gfx11 picks the row-per-lane **`dq_rows_kernel`**. *"The NaN reaches the router:
`route_kernel` never beats `-FLT_MAX` and stores `0x7fffffff` as the pick, so `moe_sort_kernel` reads
`vs[0x7fffffff]`."* With **`DS4_DQ_OLD=0`** (`dq_rows_kernel2`) the dumps are finite and every prompt length runs.

**Why it belongs in a scan of our box even though the hardware is not ours.** It is a **NaN reaching a router**, which
is a fault rather than a wrong answer, and the escalation is arithmetic, not policy: a routing pick computed from a
degenerate max becomes an unchecked index. The sibling class in llama.cpp is **#30951** (IQ1_M/TQ1_0/TQ2_0 experts emit
NaN at prompt batch > 8), and our own pack is a **Q2_0** set on a **q36** engine where the same `--fit`/VRAM gates would
report healthy service throughout. The instrument that would see it is not a rate and not a floor: it is a
**finite-check on the logit/activation dump**, which we do not currently take.

## 3. llama.cpp - batch invariance written down, and a cache/draft collision fixed

### 3.1 [GH][ENGINE] #31504 defines the kernel contract our determinism claims have been missing

Created **2026-11-01T13:56:51Z** (3 commits, ggml label, AI-assisted with disclosure). The definition, quoted from
dbsanfte's comment on the **#25618** umbrella:

> *"a kernel scoring M>1 rows at once must be bitwise identical to the serial result, because even one ULP of drift flips
> near-tie greedy picks and breaks draft acceptance."*

The diagnosis is the sentence to keep: *"Same prompt at different `-ub` values currently gives different output. Anything
scoring multiple tokens in one forward pass disagrees with sequential decoding - **batched server requests, prefix-cache
hit-vs-miss, and speculative verify steps** - which makes draft prediction heads unusable. The draft heads are not suspect:
proposing is single-row math, verifying runs the target over N>1 rows."*

**What it fixes and what it measures** (CPU, Qwen3.5-35B-A3B Q4_K_M, temp 0): integer dots for the batched q4_K GEMM
accumulated across sub-block pairs with FP scales applied once per superblock; `-fno-reciprocal-math` for the icx
quantiser; and **declining sgemm for F32/BF16 weights** rather than repairing it (the same route-around move as **#26358**
on Vulkan FA). Validation: **ub1 vs ub512 bitwise-identical logits over 140 positions at every ub in
{1,2,3,4,5,7,8,9,15,16,17,512}**; **MTP 2-row verify position-1 delta +0.25 → 0.0**; pp8192/tg128 within noise.
Remainder, stated: *"a second divergence remains past generated position 196 in 4 out of 8 battery prompts"*, and the tiled
K-quant path at `n_ubatch >= 8` is declined via `GGML_CPU_TILED_MM` rather than repaired.

**Why this is the day's most important engine item for this lab.** Three of our standing artifacts get a mechanism:
(a) the **2026-10-20 prefill artifact** - first request after a load reads ~99 tok/s and the second 50-60 because the
second prompt hits the prompt cache - is a *cache-hit-vs-miss* difference, which this PR names as an output difference
too, not only a timing one; (b) the **2026-10-08 MTP row** (+31.2 % per token, -7.3 % wall, +21.7 % tokens, letters
unchanged) sits on the same verify path whose 2-row delta this PR drives to zero; (c) the **2026-10-11 `-b 512 -ub 512`
fix** for the Kolibri flash-attention load failure was a ubatch change, i.e. exactly the variable this PR makes
numerically inert. None of our rows is invalidated - they were taken on **b11480 / b11461 / b10883**, all before this
patch - but the declaration template now has a field it did not have: **the ubatch value a row was decoded at**, plus the
honest note that pre-patch, a different `-ub` is a different answer and not just a different speed.

### 3.2 [GH][ENGINE] #31497: `--moe-cache-mib` plus a dense draft segfaulted, and the fix is four lines

Created 2026-11-01T09:39Z. `llama-speculative` loads the draft from the target `params`, overrides a few fields, and
keeps **`moe_cache_size`** - so with `--moe-cache-mib N` and a **dense** draft the draft context fails to initialise
(*"MoE cache requires a MoE model"*) and the example then **segfaults on the null context**. The patch zeroes it for the

- The author had **faster prototypes and rejected them**: *"the faster C1/C2 candidates generated about 14 % more tokens per
  second on the processor and 69-72 % more in the hybrid scenario than E, but each failed **1,586 existing strict expert-test

  they fail this contribution's compatibility requirement."*
- The accepted one is bit-exact by construction: `PMADDWD` for exact integer lane sums, the reference's eight

  Knuth's TwoSum error term and rounding to odd** because *"simply calculating in double and casting back is insufficient

  and Melquiond, Theorem 3** and the author is explicit that it is *"an implementation argument supported by tests, not a
  formal proof of this C implementation"*.

  contraction or fast-math; non-default rounding control, FTZ or DAZ fall back to the scalar reference.

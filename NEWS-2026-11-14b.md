## 1. [GH] llama.cpp: the MoE cache aborts at load on Qwen3.6-35B-A3B, the fix merged 14 minutes before this run, and no tag carries it

This is the day's most decision-relevant item and it arrived while the scan was running.

- **`#31675`**, "Eval bug: `--moe-cache-mib` aborts at load in `llama_moe_cache::impl::copy` on ROCm/HIP
  (RX 6800 XT, gfx1030, **Qwen3.6-35B-A3B**) - cache size independent", **closed 14:14:50Z**. Body: on b12110
  built from source, `--n-cpu-moe 99 --no-kv-offload -ngl 99 -c 262144 -t 8 -b 256 -ub 128 --cache-type-k f16
  --cache-type-v f16 --moe-cache-mib 2048` **aborts during the warmup decode at the end of
  `common_init_from_params`**, for 2048, 4096 and 6144 alike; **without the flag the server runs at
  ~16.5-17 t/s**. The reporter notes the same signature on the llama.cpp snapshot inside **ollama v0.40.14**
  (`39febd2ad`, 2026-10-28), so it is not a b12110 regression.
- **`#31775`**, "ggml-backend: start a new split at an incompatible weight in a split without inputs",
  **merged 2026-11-14T14:14:49Z**, merge commit `c56be864f482dc88a6d62a0816a265034941935f`, `Fixes #31675`.
  The mechanism, in the author's words, is the scheduler, not the cache: `ggml_backend_sched_split_graph` starts
  a new split at a node reading a weight from an incompatible backend **only if the current split already has
  inputs**, and a split can have nodes and no inputs. On a hybrid model with `-nkvo` the CPU split before the MoE
  block only writes the recurrent state (`cache_s_l0`), so the CUDA split after it reads nothing from the CPU;
  the router, top-k and slot-map lookup then land **in the same CUDA split** and the load aborts with
  `src/llama-moe-cache.cpp:560: the experts of layer 0 are selected in the same split as their MoE cache lookup`.
- **The fix is verified on CUDA, on our model family, by a second party.** `ServeurpersoCom`, 07:17:55Z, on an
  **RTX PRO 6000** with `Qwen3.6-35B-A3B UD-Q8_K_XL` and `Qwen3.8-Flash-Next UD-Q4_K_XL`, `-ngl 99 -ncmoe 99`:
  *"Without this PR, both models abort at warmup with -nkvo and the MoE cache... With this PR, both load, the
  cache is active and the output is coherent."* And the extra split is not free-of-charge but **profitable**:
  *"With -nkvo, prefill is even faster, pp512 397 -> 435 t/s on Qwen3.6 and 264 -> 345 t/s on Flash-Next, with tg
  unchanged"*, and without `-nkvo` split count and speeds are unchanged.
- **No published tag carries it as of 14:35Z.** Checked with the compare API against the merge commit:
  `c56be864f...b12379` -> **behind**, `...b12380` -> **behind**, `...b12381` -> **behind**, so the newest tag
  (`b12381`, published 14:24:28Z, 38 assets) predates the merge by its commit even though it was published after
  it. `compare/b12381...master` -> **ahead 3, behind 0**. The first tag that can carry it is the next one.

**Why this is ours and not a curiosity.** Our MoE-cache ladder (2026-10-20, re-run 2026-10-31 and 2026-11-01)
declared `--cpu-moe --load-mode none` and **never `-nkvo`**, so **no recorded row is invalidated** - but the abort
condition is *exactly* our shape otherwise: a hybrid MoE model (`qwen35moe` / Qwen3.8 Flash-Next), experts on the
CPU, a declared `--moe-cache-mib`. Any future arm that adds `-nkvo` to save KV offload on a build before #31775
**fails at load, it does not measure**. Declared rule: `-nkvo` + `--moe-cache-mib` on a build without #31775 is
VOID before start, and the check is one `src/llama-moe-cache.cpp:560` pattern in the log.

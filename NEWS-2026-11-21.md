## 1. [GH] `#6478`: expert-cache hit rate falls **96.8 % -> 64.5 %** from engine 0.1.53 to 0.1.63 at the same slot budget, and the route-tail default explains only a third of it

**`#6435`** (open, 2 comments, created 2026-11-20T19:31:06Z, **RX 9070 16 GB, Windows 11, 32 GB RAM,

## 6. [GH] `#6480` / `#6327`: two mechanisms that make a prefix **not a prefix**, both with the fix already in the tree

**`#6480`** (created 2026-11-21T07:35:41Z, open, 0 comments; the reporter notes it is the same report as
`#5758`, closed for a missing title prefix and **not fixed**): with thinking off, the **chat template baked
into the Qwen3.6 pack writes an empty think block on the first answer and then leaves that block out of
history**, so the next prompt is not the same prefix and **reuse is 0**. The measured shape: short turns go
**0 reused -> 36 of 52** after rewriting one condition, and a follow-up at ~70k tokens **waited 200-213 s
before the first token** while a hand-fed prefix reused 14 of 15 - the reporter's own estimate is 20-40x less
waiting, marked as an estimate because the 70k case was not re-run.

**`#6327`** (open, updated 2026-11-21T11:06Z; created 11-19, so this is a status update, not new coverage):
**compaction re-reads 331K-342K tokens five times at 19.5-20.1 min each**, and the cause is a **cache budget**
- the auto budget is **3,840 MiB** while one snapshot at ~340K is **5,742-6,926 MiB**, so the conversation is
never parked and the compaction request is read from token 0. With the budget sized to hold one snapshot of
`--max-context` (PR `#4338`), a real `/compact` **reused 282,077 of 282,474 tokens (99.86 %) and prefilled in
3.8 s**. The documented opt-in path in `serve/server.py` measures **84,895 / 84,997 reused (99.88 %)** against
**41 / 80,683** without it.

This is the append-cost question this lab has carried since 11-17, and it now has an arithmetic answer:
**a cache smaller than one snapshot of the context makes every compaction a full pre-read**, and the number to
compare against is our own `--conversation-cache-mib` declaration, which no row of ours records.

The memory item is **`#17902`** (2026-11-21T14:17:35Z, AI-authored, declared) with fix PR **`#17901`**:

- With Dynamic VRAM and async offload, **each offload stream has its own cast buffer**, and a buffer grows to
  fit the largest thing sent through it and is not released until `reset_cast_buffers()`.
- `cast_modules_with_vbar` (`comfy/ops.py:151-165`) has a guard meant to keep the largest cast weight on one
  stream. **It compares against a local `cast_buffer` that is always `None` when the guard runs**, so the
  current size always reads 0 and the guard takes the next stream **on every cast of the largest weight**.
- Measured on **Windows 11, 16 GB NVIDIA, torch 2.14.1+cu130, comfy-aimdo 0.6**, generating with Gemma 4 12B:
  the tied embedding and output head `model.embed_tokens.weight` is **1,920 MiB** and is cast for every token's
  logits; the next largest weight is 56 MiB; **both streams held a 1,920 MiB buffer**. *"That VRAM comes out of
  the resident weights, so more of the model is streamed on every step."*

That is the third cast-buffer/VBAR item this month (11-15 `#17122`, 11-20 `#17837`, today `#17902`), and the
first with a **per-stream size** rather than a pin. An image arm on 12 GB with Dynamic VRAM on - the default -
loses up to two head-sized buffers to this.

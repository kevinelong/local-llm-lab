## 2. [GH][VRAM] ComfyUI: one model, one card, three memory bugs - and each fix is proved bit-identical

All four issues were filed within **one minute** of each other (**2026-11-11T23:02:58Z -> 23:03:05Z**) by the same
reporter, on the same box: **ComfyUI v0.45.0** (code checked unchanged on master `b2f6707443`), **comfy-aimdo 0.6.0**,
**comfy-kitchen 0.2.41**, **PyTorch 2.15.0+cu132**, **RTX 3060 12 GB**, Linux, **Dynamic VRAM on (default)**, the
official `video_fastvideo_fasth3_*` templates at length 362 (15 s) 1344x768, **~109k video tokens**. Each says *"Filed by
Claude Opus 5.5 in Claude Code"* - which is now a normal provenance line on this repo and should be recorded as such.

### 2.1 `#17703` - the MLP materialises all 109k tokens at once: 6.3 GB for one matmul

`MLP.forward` runs `comfy.ops.linear_input_act(self.fc2, self.fc1(x), "swiglu")` over every token. `fc1` outputs
`ffn * 2 = 28672` features, so the buffer is **6.3 GB bf16** and `torch.empty` fails in `comfy_kitchen`'s `int8_linear`.
`DiTBlock.forward` also keeps the full-size MLP output and two normalised copies of the stream alive.

The proposed fix chunks the MLP at 16384 tokens, adds each chunk's gated output **in place** into the residual stream,
and drops `h` before the second norm: peak **~0.9 GB**, and *"matched the original bit for bit (max diff 0.0)"*. The
block also `del h`s after attention, which the original does not.

**Why it is our item:** the failure is an **activation** peak on a **12 GB** card, not weights - the same shape as our
image arms' floor breach, and the fix is free.

### 2.2 `#17701` - the malloc graph keeps its pages between sampling steps

`MiniMaxH3Model.forward` calls `comfy.model_prefetch.malloc_graph_begin()` around the blocks, but
**`cleanup_malloc_graph()` only runs from `cleanup_prefetch_queues()` when sampling ends**. From step 2 the arena keeps
its physical pages, so the next ordinary allocation fails - here the **40 MB** `model_output.float()` inside
`calculate_denoised`. At the failure `torch.cuda.mem_get_info()` reported **~28 MB free while PyTorch held under 700 MB**,
and `--vram-headroom 1.5` changed nothing; an aimdo DETAIL trace showed `vbar_mb=0`, i.e. not weights.

Fix: release the graph after each forward on long sequences. Local result: **step 130 s -> 117 s**, plus no OOM.

### 2.3 `#17700` - the RoPE table cache can never hit

`SparseAttnPatch.vsa_rope_freqs` keys its cache on `weakref(rope_freqs)` **and** `plan`, while `_run_blocks` builds a
**new** `rope_freqs` every forward - so from step 2 the cache misses and each step allocates a second padded table while
the old one is still referenced. The fix keys on the plan plus the tensor's **shape/dtype/device** and drops the old
entry **before** allocating. *"output matched the original bit for bit (max diff 0.0)"*.

### 2.4 `#17702` - the second offload stream's cast buffer grows after block 0

With Dynamic VRAM each async offload stream gets its own aimdo cast buffer, grown on first use to the largest casted
weight (**424 MB** for an H3 int8 block). Block 0 uses stream A; by block 1 - stream B's first use - *"its activations
leave very little VRAM"*: `block 0 start: torch_alloc=410MB ... cuda_free=7052MB` then `block 1 start: torch_alloc=541MB
... cuda_free=148MB`, and the grow fails with **`VRAM grow failed: 424159232 bytes`**. Text-to-video passed only because
stream B's buffer had already grown earlier in that run. **Workaround: `--async-offload 1`, at 10-13 % slower steps**;
pre-growing both buffers crashed with `cudaErrorInvalidValue` from `cuMemFreeAsync`.

### 2.5 `#17704` - Dynamic VRAM silently drops a LoRA patch, measured in pixels

The item that ties the burst to our instrument. With Dynamic VRAM on (the default), a patch on a parameter of a module
**without `comfy_cast_weights`** is never applied and nothing is logged - the load line even reports **`0 patches
attached`**. Qwen-Image 2.1's `txt_in.text_norm` is a plain `nn.Module` (`ZeroCenteredRMSNorm`), so it is the case.
Same workflow, same seed, 1024x1024, 20 steps, comparing each patched render with the unpatched render **in the same
mode**:

| patch | dynamic VRAM (default) | `--disable-dynamic-vram` |
|---|---|---|
| `txt_in.text_norm` (no `comfy_cast_weights`) | **0.000, 0.00 % of pixels: identical image** | 47.8, 99.98 % |
| `txt_in.in_layer` (cast module, control) | 2.16, 98.6 % | 1.88, 98.5 % |

And the two **no-patch** renders (dynamic vs static) are **pixel-identical**, so the modes differ only in the patch. A
contributor claimed it at **2026-11-12T05:55:03Z** (*"fix it so patches on plain `nn.Module` parameters attach the same
way in both modes (or at minimum fail loudly)"*).

### 3.1 `#5852` - Q2_0 at `--kv int8` is 12.3-12.4 KiB/token, `q4_0` is 6.9, and `--kv-resident` is the VRAM lever

New, **0 comments**, **2026-11-12T11:34:18Z**. Hardware: **RTX 5090 32 GB (sm_120)**, 2x Xeon Gold 5218 (no AVX-512),
**PCIe Gen3 x16**, 125.6 GiB RAM, Qwen3.8-Flash-Next **Q2_0**, **engine 0.1.47** (ours), Docker image **0.2.2-cuda13**,
one request at a time. Measured from the engine's own start line (`the K/V in ... of pinned RAM`):

| context | `--kv` | `--kv-resident` | K/V in pinned RAM | KiB/token |
|---:|---|---:|---:|---:|
| 65,536 | int8 | 32,768 | **0.77 GiB** | 12.3 |
| 262,144 | int8 | 16,384 | **3.09 GiB** | 12.4 |
| 524,288 | q4_0 | 16,384 | **3.38 GiB** | 6.9 |
| 1,048,576 | q4_0 | 32,768 | **6.75 GiB** | 6.9 |
| 1,048,576 | int8 | 32,768 | **12.38 GiB** | 12.4 |

`[INFERENCE]` at our declaration - **65,536 context, `--kv int8`** - that is **0.77 GiB of pinned host RAM**, and
`--kv q4_0` would be **~0.43 GiB**. We have never declared that number, and it is now measured rather than derived.

The failure it explains: at **1M context with `--kv int8`** the engine starts and dies -
`expert cache auto: 0.52 GiB free ... -> 0 slots`, then
`prefill: device buffers for a chunk of 1024 tokens do not fit (1 of 32109 MiB free ...)` twice, then
`the GPU has too little free VRAM for the prompt path`, `The server did not become ready (failed: server_exited)`. The
engine's own advice names context, `--kv q4_0` and `--vram-reserve-mib`; the prompt-path line names `--prefill`; **the
flag that actually moves it is `--kv-resident`**, which *"is not mentioned as a 32 GB lever anywhere I could find"*.

Its numbers: `--kv-resident 32,768` -> **1,147 slots, 76.7 tok/s**; `16,384` -> **1,209 slots, 82.5**; and on the same
card with another 5.5 GB free, `16,384` -> **7,302 slots (10.27 GiB), 93.8 tok/s**, decode cache hit **92-93 %** against
**48-58 %** at 897-1,147 slots with **30 pool workers at 1,011-3,000 % CPU**. `--pool-cores` pinning 12 logical
processors took CPU from 30.7 to 12.0 cores and decode from **76.7 to 34.8** - *"halving the CPU halves the speed,
because those threads are doing the work the cache cannot."*

### 4.1 `#19670` - an iGPU with a firmware carve-out must not be capped at free system RAM

## 1. [REL][ENGINE] Strata 0.2.13 / 0.1.59: defaults moved into the engine, eight switches deleted, and the fit label stopped counting the lookup table

Published **2026-11-09T12:46:51Z** (`created_at` 10:12:22Z), `prerelease: false`, **42 assets, 9.70 GiB**. Windows
installer **113,296,921 B**; Control zip **73,567,347 B**; DSV4.1 CUDA 13 **422,621,585 B**. Both drafter packs are
byte-identical to 0.2.12 (`...q4_0-selq4.pack` 339,694,592 B, `...bf16sel.pack` 522,458,112 B). Bump target is now
**app 0.2.13 / engine 0.1.59 / Control 0.1.59**; `strata components rollback` returns the engine to 0.1.58 with Control
staying 0.1.59.

### 1.1 The three changes that alter how a row reads

- **Launcher-written settings are now the engine's own defaults.** The release names them: *"the parallel stack on
  Linux CUDA with 2 or more slots, the GDN settings on Linux CUDA, the chunked GDN scan on Linux with all cards gfx12,
  the gfx1151 hipBLASLt table, the Q8_0 hyper-connection read for Unsloth UD files on CUDA, and fp16 decode windows on
  the Mac for a resident IQ3_S or Q2_0 pack."* The stated intent is that *"a plain engine start matches the app and the
  Terminal"*. Consequence: **a config that declared nothing inherited the launcher's value before and the engine's own
  value now**, so the same saved config is not the same condition across this boundary. The Windows CUDA part of that
  list is one item (the Q8_0 hyper-connection read for Unsloth UD files), so our own line is affected in one named place
  - and the Unsloth UD read is exactly what `#5296` below is about.
- **Eight opt-in switches are gone** (`STRATA_METAL_ROUTE`, `_METAL_PARTIAL`, `_METAL_WPF_MIB`, `_MMVQ_PF`,
  `_MMVQ_SG`, `_GR_Q32_PL`, `_DF2_GATE`, `_DF2_ROW_MS`), described as *"finished experiments"*. A declaration list that
  still carries them now names settings that do nothing - the class we recorded on 2026-10-29 (`"=0"` forms a SYCL
  launcher drops) and again 2026-11-06 (an env name that does not reach the engine). **`docs/SETTINGS.md` is new and
  lists every setting**, which is the registry we have been rebuilding by hand since 2026-10-22.
- **The fit label changed what it measures:** *"One fit label in the app and the Terminal: 'fits' when the model files
  **without the lookup table** fit graphics memory plus RAM, otherwise 'may run slower'."* The reason given is that the
  Unsloth sets *"used to be measured against RAM only, which showed 'too big' on a V100 32 GB with 31 GB of RAM"*. On
  our pack the lookup table is the **28.8 GB** shard the release notes of 0.2.10 already called "the model reads per
  token" (`NEWS-2026-11-05`), so **a "fits" label now excludes the largest single component we might have to map**.
  `[INFERENCE]` a fit label read from 0.2.13 is therefore not comparable with one read from 0.2.12, and neither is a
  substitute for our own commit/VRAM gate.

| Strix Halo, UD-Q4_K_XL | 46.6 | **49.1 (+5.2 %)** | differs on **30 of 36** prompts, same on every run |

answers of 300 tokens."* The two declarations that bound every one of those rows, verbatim: **"Speeds were not measured
again on the final 0.1.59 packages"**, and **"Other machines and models were not measured again."** So the delta is a
settings delta between two configurations, not necessarily an engine delta.

- **DFlash2 window and confidence per card.** Strix Halo window **5 -> 8**; **Blackwell cc 12.0 with 48 GB or more**
  window **6 -> 8**, confidence **0.35 -> 0.55** for IQ3_S. **Our card is cc 12.0 with 12 GB, so none of this applies
  to us** - and the release says it: *"The DGX Spark and other cards keep their 0.2.12 values."*
- **On the cards where Auto picks MTP (for example 12 GB cards), the first load from the app's setup screen runs
  without a drafter**; the next Load from the Models page fetches it. It is listed as unchanged from 0.2.12, so any

  `STRATA_HIPBLASLT_TABLE=on` restores it. Not our backend, recorded because it is the second time this window that a
  vendor silently reverts a tuned default.

### 1.3 The two items in it that touch our card by name

- **First launch of a fresh install on an RTX 5070 took 398-406 seconds**, against **107-118 s on 2026-11-07** and
  **398 / 595 s** for the same install on 0.2.12 the same day; Strix Halo **337-411 s**. The vendor states
  **"We did not find the cause."** This is our exact card, and it is the `startup_wait_expired` class we recorded on
  2026-10-22/23 and again on 2026-11-08 (`#5585`). **A fresh install is therefore not a usable timing baseline**, and a

- **A fix on Windows Strix Halo removes the engine's 2,560 MiB floor on integrated graphics** (22,991 expert-cache
  slots against 17,556 on 0.2.12) - the same *kind* of object as the GPU reserve our gate already declares, applied to a
  platform we do not run.

### 1.4 The rest of the release, one line each

- **Intel Arc determinism:** *"the same prompt gives the same answer on every run. 50 of 50 runs were identical on an
  A750, against 3 to 5 different answers in 5 runs before."* Cause named: oneMKL's small bf16 matrix products *"changed
  from launch to launch"*, so **Strata's own fixed-order kernel** replaces them; prompt speed is 0.995-1.004 of before;
  `STRATA_SYCL_BF16_DET=0` restores oneMKL. This is the fourth vendor in a month whose *library* is a non-determinism
  source, and the first where the fix is a fixed-order reimplementation rather than a seed.
- **Linux `#5327` (PR `#5531`, pjgmobile):** *"an expert-arena shortfall that the file cache can cover loads through the
  file cache again"* - see §2, where this is a `q2_0` decode regression, not a Linux nicety.
- **App start:** main file **3.12 MB -> 0.76 MB**, start screen **248.5 -> 143.4 ms** (headless Chrome, median of 10).
- **Qwen4 groundwork:** *"a model of a new shape gets its own engine download (`strata-q4-<shape>`) beside the Strata
  engine"*; the engine reports its shape with `strata --geometry` and Control checks it against the signed manifest.
  **The 0.2.13 feed has neither a model list nor a shape engine yet**, and 0.2.12 and older ignore the new feed members.
- **Fixed:** feed models no longer stop an install with `KeyError 'mmproj'`; a model with no draft layer no longer
  fetches the Flash-Next drafter; a model of another shape gets a neutral expert profile; **the low-RAM mode no longer
  writes a second copy of the experts**.
- **Known problems left open:** peer mode (`--peer-device`) faults on its first request in **~4 % of fresh starts**;
  **Radeon gfx1201 with DFlash2 chosen by hand can stall on the prompt** (11 of 50 engines on 0.2.11); Intel Arc in the
  desktop app stops with "no NVIDIA GPU found" at model setup; Linux AppImage does not reopen itself after an in-app
  update; **Mac final files were not run with a model at all**.
- **What the vendor ran on the release files** includes *"plain, two-turn and tool chats on Windows (**RTX 5070 with
  Gyro-S**)"* - so our card is in the tested set for the first time since 0.2.10, though with a pack we do not hold.
- **Dating note:** the release's own feed was **generated 2026-11-09T09:33:27Z**, **3 h 13 min before** the release was
  published at 12:46:51Z. So the feed's `generated_at` is not the release's date, and `strata update` seeing
  "sequence 123" dates the feed, not the package.

**Applies to us:** yes, as a **declaration change**, not a speed claim. Item 1 of the shortlist.
**Instrument:** the declaration template (`DECLARATION-TEMPLATE` from 2026-11-08). **Cost:** an edit; zero engine time.

*"the 28.8 GB lookup shard stays memory-mapped"*. Args: `--expert-cache auto --prefill auto --spec 4 --spec-min-p 0.5

### 4.3 `#5659` - the output head is worth 2.4x decode when it is on the host, on a card too small to hold it

Created 2026-11-09T13:03:09Z, 0 comments, with a patch linked (`STRATA_CPU_HEAD=1`). The engine already warns
*"short of GPU memory: the output head (497 MiB) moves to pinned host memory and is read over PCIe for every logits
row"*; the reporter's A/B on an RTX 3070 Ti Laptop 8 GB (PCIe 12.0 GB/s as the engine reports it):

| head | ms per verify window | decode |
| --- | ---: | ---: |
| in VRAM | 25.4 | **46.4 tok/s** |
| in pinned host memory (`STRATA_HEAD_HOST=1`) | 67.4 | **19.6 tok/s** |

The arithmetic is the finding: **42 ms per window for a 497 MiB Q6_K head is ~12 GB/s, i.e. PCIe speed**, while the same
engine's CPU kernels read Q6_K at **47.6 GB/s with 8 threads** (`kq_cpu_bench --pairs q6_K/q8_0 --threads 8 --nt 1`), so
the same rows cost **~11 ms on the CPU**. This is the cleanest measured statement of the host-head penalty we have, and
it applies to any card where the head is the first thing that does not fit - *"anyone running Qwen3.8-Flash-Next on a
4-6 GB card"*. Our 12 GB card keeps the head resident, so it is a **sensitivity, not our failure mode**: it prices what
the head costs the moment it moves.
**Cost:** zero; a declaration line ("head in VRAM or in pinned host, and the ms per verify window if the engine prints
it").

### 9.1 `2611.09825` - BitDecoding-FP4: native FP4 KV decoding (submitted 2026-11-06)

The abstract states the gap precisely: *"4-bit microscaling formats (NVFP4, MXFP4) shrink the cache and run attention on
FP4 Tensor Cores,"* but existing FP4-KV systems *"use vanilla quantization that causes severe accuracy drops, whereas
accuracy-oriented 4-bit algorithms rely on vector codebooks whose lookup overhead degrades decoding throughput."* Its
fix is an algorithm-system co-design, and it mitigates three error sources, the first described as **"Dual-Residual
Query Quantization splits queries into two FP4 tensors, cutting query logit error from 60 % to 1 %"**.

**Why it is on our axis:** our notes have carried the sentence *"FP4 KV ships in the model while both our engines refuse
to demonstrate it"* since 2026-10-29 (llama.cpp `#31291` closed for want of benchmarks; Strata's `--kv q4_0` *"did not
reproduce a gain"*). This paper says **the accuracy failure is in the query, not in the cache keys** - which explains why
a naive `q4_0` cache measured as a wash and why nobody could demonstrate it. It also gives the metric a KV-quant row
needs: **logit error on the query, not just perplexity** - the same lesson `2610.37126` and `2611.07605` taught from the
pruning and eviction sides.

### 9.2 `2611.09424` - MINE: lossless entropy coding for single-stream decode (2026-11-06)

The premise is ours exactly: *"Single-stream decoding is strongly memory-bound, since every weight must be streamed from
memory once per generated token and requests cannot be batched in local or low-latency deployments."* It adapts **dtANS**
to LLM inference (*"dtANS-LLM"*), exploiting *"the non-uniform distribution of weights, which persists even after
quantization"*, with hyper-parameters that trade compression against throughput. Crucially it aims at what prior
lossless methods did not: those *"yield speedups only for specific data types such as BF16 and under additional
assumptions"*.

**Why it is on our axis:** our decode is bandwidth-bound at **~0.527 GiB of expert bytes per token** (`NEWS-2026-10-20`,
and the 2026-11-08 rate check), and our measured **60-70 % of achievable bandwidth** is the honest headroom. A *lossless*
code above the quantiser is the one class of compression that cannot move answers - which is the property our pack
decisions keep being unable to buy (§4.1, `2611.07654`).

### 9.3 `2611.09709` - RidgeFill: fill the late-layer KV cache from a prediction instead of computing it (2026-11-06)

*"RidgeFill shortens prefill by not computing most of a model's upper layers for the prompt. The lower layers run
exactly up to a split; from the split layer's state a per-layer map predicts every later layer's input, and each late
layer writes its cache from that prediction."* It is a **retrofit** of what **YOCO and DeepSeek-V4.1-Flash do natively**
(*"where the projection is trained into the model"*): the map is *"a ridge regression fitted once in closed form from one
pass over calibration text"*, *"the layer's own projections run unchanged"*, and *"a chosen set of rows, the last few
thousand tokens, and every decoding step run the full model. Nothing is trained and no token is dropped."*

**Why it is on our axis, and the most decision-relevant item in the section:** our reference model is
**DeepSeek-V4.1-Flash's** architecture family relative, and Strata already ships the *trained* version of this idea as a
product - `NEWS-2026-10-24` recorded *"prompts over ~3,700 tokens skip work the last 20 layers cannot use (16K ~34 %
faster, top-1 unchanged in 99.5 % of 799 positions)"*. So **this is the published form of a 34 % prefill win we have
never measured as a switch**, and it comes with the honest instrument note (*"Most of the work was in measurement"*) and
a calibration-text dependency - the same provenance problem as our `.strp` expert profile (shortlist item 6 of
`NEWS-2026-11-08`) and as `2611.07654`'s calibration-language result.

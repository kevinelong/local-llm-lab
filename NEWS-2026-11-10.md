### 1.1 `#26014` - the Windows unbuffered read path, merged 2026-11-09T18:22:09Z

+504/-35, **3 files**, merge commit `9d340ec341`. The body's framing, verbatim: *"Linux supported unbuffered reading
from disk via DirectIO for fast model loading. On my machine with PCIe5.0 NVMe drive this path increases the model
loading performance from 1-3GB/s to >9GB/s. For Windows this change is needed, as using mmap of large models on setups
with small CPU RAM lead to Sysmem pressure and eviction of runtime pages."* It *"introduces the unbuffered read file API
of Windows"*; the Linux half is `#18012`, merged earlier.

- **The 9 GB/s figure is the Linux DirectIO number, on the author's machine.** There is **no Windows before/after** in the
  body, and the testing section is a request (*"I'd appreciate it if people could test this PR on different devices"*)
  rather than a result. So today's honest claim is: **the code path changed; the Windows speed is unmeasured in the PR.**
- **Why it could matter here.** Two of our recorded effects are file-cache effects: the 2026-10-27 ladder's arms that the
  engine called *"the file cache can keep them"* decoded **23.1 / 87.0 tok/s** against **4.1-16.6** for the eight it did
  not, and the Windows working-set leak (`#31709`, `NEWS-2026-11-09` section 5.4) is the same page-population story from
  the other side. A load path that bypasses the page cache changes **both** what a fresh start reads and what it evicts.
- **Our engine is b11480**, which predates this by 753 builds. This is a third reason a staged download is worth doing,
  beside `#30966`/`#31888` and the deterministic Top-K.

## 2. [GH][ENGINE] Strata `#5626`: the prompt-path CPU share is on by default and chosen from per-process timing, so temperature 0 is not repeatable across processes

`#5626`, open, **0 comments**, filed **2026-11-09T16:23:48Z**, title *"[Engine] Reproducible output: the documented
recipe misses the prompt-path CPU share (`auto` picks its layers by timing, so the same request differs between
processes)"*. This is the most consequential item of the window for us, because it is about **our own class of claim**.

The setup and the finding, in the reporter's words and code references:

- The documented recipe for byte-identical repeats - `STRATA_IQ_MT_MIN=1` plus `--prompt-cache 0 --adapt-swaps 0
  --pcie-frac 0` - *"is not enough"* when the prompt-path CPU share is on.
- **The share is on by default on one CUDA card and on one gfx12 card** (`prefill.cpp`, annotated *"0.1.41: ON BY
  DEFAULT"*), and opt-in elsewhere via `STRATA_PREFILL_CPU_SHARE=auto`. Our engine line is 0.1.47, so **every single-card
  Strata row we have was taken with it on**.
- With `auto`, **two quantities are measured with CUDA events while the prompt is read**, so they differ per process:
  (a) whether a layer shares at all - `cpu_arm` alternates until 3 ratios are in, then a median wall ratio `cpu_gate`,
  with a probe every 29th layer; and (b) how much it shares -
  `cpu_share_now = clamp(g / (c + g), 0.05, 0.9)` from running means of CPU and GPU time per expert.
- *"Which experts go to the CPU is deterministic once those two are fixed (fewest tokens first)"* - so the only
  non-determinism is the timing-derived pair. Logged with `STRATA_DBG_CPU_GATE=1`: **two processes shared 23 and 36 of
  42 eligible layers** on the same request.
- **A fixed share removes both**: `STRATA_PREFILL_CPU_SHARE=0.5` or `0` gives byte-identical repeats.

Their rig: 2x RX 6900 XT with a layer split, Qwen3.8-Flash-Next GSQ-RCO-IQ3_S (native GGUF experts), ~400-token picture
prompts **below `STRATA_PREFILL_STREAM_MIN`** so every arm takes the staged path and only "who computes the non-resident
experts" differs, greedy, decode residency pinned (`--adapt-every 0 --pcie-frac 0`), one fresh engine process per run.
The measurement table itself was cut off in this read; the mechanism and the two-value comparison are what I quote, and
I do not quote a rate from it.

**Applies to us:** yes, and it retroactively constrains three things we hold. (1) The 2026-10-08 MTP row already could
not be quoted as a determinism result; this adds a second, independent reason on the Strata side. (2) The 2026-10-20 q1
row (`--kv-resident 32768` vs streaming, letters 92/93 in all four arms) compared **answer letters across separate
processes**, which this says can differ. (3) The 16 GiB-vs-2 GiB resident ladder's "greedy text identical in 20 of 20"
(2026-11-01) was lucky rather than guaranteed - and its identical text is *evidence the share did not flip in those 20*,
not evidence the engine is deterministic.

**Instrument that already exists:** the declaration template's determinism block. **Cost:** an edit that adds
`STRATA_PREFILL_CPU_SHARE` beside `ubatch` and the build gate, plus one two-start check to confirm the flag is honoured on
0.1.47 (the engine is under `ai_bench`, so that check is a normal session, not this scan).

### 3.1 `#5714` - a refused page-lock costs 60.9 s before anything else happens

Open, 0 comments, 2026-11-10T12:12:22Z. Windows, RTX 5080 16 GB, **128 GB RAM**, engine 0.1.59, launch config carrying
`--resident-budget-gib 104`. The engine first tries to page-lock the whole complement, Windows refuses, and it falls back:

```

FileExpertSource: page-locking refused (out of memory); trying pageable memory
FileExpertSource: locked resident cache complement ready: resident 101.81 GiB, pinned 0.00 GiB in 107 s; ... locked 104256 MiB via working-set minimum + VirtualLock
```

Three timestamped facts, in the reporter's own reading of the log: **the refused `cudaHostAlloc` alone took 60.9 s**
(11:52:03.787 -> 11:53:04.735), then ~30 s before the copy began, then 17 s of copy: **107 s total**, on **all 9 chat
starts** (8 at 104.00 GiB, one trimmed to 101.81) and **5 runs of `tools/quant_quality.py`** (101-119 s each). And it
works lower: one start the engine trimmed to **99.25 GiB** logged *"mapped pinned cache complement ready: resident 99.25
GiB, pinned 99.25 GiB in 34 s; page-locked and mapped"*, and `--set resident-budget-gib=99` gave **"pinned 99.00 GiB in

### 8.1 `2611.11533` - Ostinato: "resident experts in every forward pass", and it names the 32-token cliff (submitted 2026-11-08)

The framing sentence is about this lab's engine: *"this http URL's expert cache skips forward passes of more than 32
tokens to keep the experts of decode cached, so an agent waits **2.1-2.8 s after each tool output**, whereas its default
layer placement shortens this wait but is **1.5-1.6x slower in decode**"*. The insight: *"a short prefill touches too
many distinct experts to upload, yet sends **84 % of its expert activations (routes) to a stable set of experts that fits
in GPU memory**"*.

The mechanism, in the abstract's own terms: short prefills **split their routes**, leaving *"fewer than one of a token's
six routed experts per layer to the CPU"*; long prefills **upload each distinct cold expert once**; each decode step runs
as **one fixed-shape CUDA graph per GPU**; and it is *"without changing what the model computes"*. Numbers: on real coding
and customer-service agent sessions with **DeepSeek-V4-Flash on four RTX 4090D**, *"Ostinato is the fastest engine in both
phases and finishes every session sooner than all six baselines"*, cutting median post-tool wait **22-55 %** and finishing
sessions **1.4-2.5x sooner** than llama.cpp and KTransformers.

- **Applies as a prediction our own ladder already half-tested.** Our q2 ladder (2026-10-20) found **prefill gains first**
  (72 -> 93 -> 101 tok/s by a 512 MiB rung) and decode gains last - consistent with "a cache sized for decode is skipped
  by long prefills" only if the prefill gain came from the *small* rungs, which it did. The paper's claim that a **short**
  prefill is where the cache fails is the mechanism that would explain the **512 MiB dead zone** we measured

- **Instrument:** a build that logs the per-ubatch hit rate (the `ubatch <= 8: 42.49 % / ubatch > 8: 0.86 %` lines recorded

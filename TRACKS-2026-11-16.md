# Two tracks, two measurements, and no single table

Kevin, 2026-11-16: there are two questions here and they rank models differently. Every composite ranking this lab has
produced so far mixed them, which is why a model can look "best" in one note and useless in the next.

**Track A - the fastest local task agent.** It gets a bash shell, a workspace and a programming job, and it has to
finish inside a wall. Throughput, tool use and instruction-following decide it; breadth of knowledge barely matters.

**Track B - the most knowledgeable model that will answer, for broad research.** It reads long, heterogeneous
documents and answers questions, including benign-but-sensitive ones. Breadth and **willingness** decide it; speed is
recorded and never ranked.

**The rules that keep them apart**

1. A row names its track. `track: A` or `track: B` is the first field, before any number.
2. **No composite score.** There is no "best model"; there is a Track A order and a Track B order, and a model may be
   first on one and last on the other.
3. Speed is **ranked in A** and **recorded in B**. Knowledge is **ranked in B** and **recorded in A** (it is not
   irrelevant - a coding agent that cannot read a spec fails - but it is not what decides A).
4. A model enters each track by passing **that track's** gates. Passing B's gates says nothing about A.

## Track A - fastest local task agent

| field | what it is |
|---|---|
| **primary metric** | **`tokens/wall-second`** on the frozen coding protocol - the whole task, including prefill, every turn and every tool call. Not decode tok/s; decode has never predicted this (`Kolibri` 42 tok/s decode, 32 effective). |
| **success metric** | checks passed on the **discriminating** subset - `ledger2` (226), `repo` (78), `repo2` (55), `perf` (33) - because `events` and `paths` are saturated for anything competent (2026-10-09) |
| **reliability** | `clean_finish` is **not** a failure signal (it appears on perfect runs); what is a failure: a reply cut at the cap with no tool call, an artifact byte-identical to the starter, or a script that does not import |
| **stability** | n **>= 3** on one task, reported as a **rate**, never a single run - `ledger2` has a measured spread of **14-19 checks** |
| **gates** | parser + host smoke pass; **>= 8 tok/s decode** implied by the 720 s wall on this suite; context 131,072 with KV resident; resource floors unchanged (9 / 8 / 0.5 GiB) |
| **declarations** | build + commit, quant, `-b/-ub`, context, `--parallel`, provisioned caps (32,768 reply / 131,072 context), tool-call probe result |
| **invalidates a row** | a different `-b/-ub` (pre-#31504, a different ubatch is a different answer), a build on the other side of a numerics merge, a stale engine (the 2026-10-22 contaminated-server class), and any run where another model was resident |

Measured so far: `Qwen3.6-35B-A3B Q4_K_M` **414/414**, 274 s/task (the only configuration perfect on both hard axes);
`gpt-oss-20b` fastest at **176 s** but `repo` **0/78**; `Kolibri-1` 99.5 % at **1.8x** the time; the dense **27B at
4.3 tok/s** cannot finish a task inside the wall - it is not a Track A candidate at any quality.

## Track B - most knowledgeable, most willing

| field | what it is |
|---|---|
| **primary metric** | **knowledge accuracy** on the pinned 1,100 items, with its **paired SE of 1.33 pt** quoted - a gap under ~2 points is not a difference |
| **resolution problem** | 1,100 items cannot separate models closer than ~2 points. Before ranking anything within that band we need more items or a harder slice; a "tie" is the honest answer until then |
| **coverage** | **the missing instrument.** A fixed probe: ~20 benign-but-sensitive prompts, ~10 genuinely harmful, ~10 ordinary. Two numbers: **coverage** (complies on the benign-sensitive class) and **guard** (refuses the harmful class). 100 % coverage with 0 % guard is a defect, not a win - an agent must be able to decline |
| **long context** | a needle/recall probe at 32K and 128K, because research means long documents; `longctx` (40) and `longctx2` (40) are the frozen proxies |
| **speed** | recorded (decode, prefill, wall per 1,100 items) and **not ranked** |
| **gates** | it runs - resident in 63.5 GiB or streamed from SSD; a **declared** wall budget for one full knowledge run; coverage and guard both measured |
| **declarations** | base model, quant, **`decensor_method`** (`abliteration | heretic | data-finetune | none`), calibration text (or `UNVERIFIED`), pack revision, context |

Measured so far: **88.5 %** (Qwen3.6-35B-A3B Q4_K_M) vs **89.7 %** (Qwen3.8-Flash-Next Q2_0) - 13 items, **1.33 pt SE**,
i.e. **not a difference**, and neither publisher declares calibration, so the tie may not be read as a bit-width
property. The dense 27B has never been measured on this instrument, and at 4.3 tok/s one run is **~18 h** - which is
affordable **because it is Track B**, not despite it.

## The memory budget is the other half of the split (Kevin, 2026-11-16)

The two tracks do not compete for the same resource. This is why a pack that is hopeless for one is ideal for the other.

| | Track A - agent | Track B - knowledge |
|---|---|---|
| **context** | **as much as practical** - our measured configuration is **131,072**, and the frozen coding protocol's prompts reach ~65k in `longctx` | **small**: the knowledge instrument's items are single questions; **8,192 is ample**, and that is a measured property of the items, not a guess |
| **KV cache** | the binding constraint. Context buys KV in bytes per token, and every token of it competes with the expert cache for the same VRAM: on the q36 path fp32 KV was measured at **45,056 B/token** (~1.4 GiB at 32K, ~2.8 GiB at 64K) before int8; the whole 2026-10-27 chunk/reserve/cache ladder exists because those three trade against each other | **negligible**: no residency, no conversation cache, no prefix reuse to engineer. `--kv-resident 0` is not a compromise here, it is the correct setting |
| **weights** | bounded by what is left after context, KV, workspace and cache - which is why the 35B Q4 class is the ceiling there | **everything left goes to weights**, and because the KV term is ~zero, the pack is the only limit |
| **what it means for candidates** | a 70 GB or 231 GB pack is **out of the question**: the context would have nowhere to live | the same packs are the **whole point**: `Qwen3.8-Flash-Next` Q2_0 abliterated (~70 GB, streamed) and **DeepSeek V4.1 2-bit abliterated (~231-249 GB, streamed)** are Track B candidates *because* they need no context |

**Consequences, stated so they are not rediscovered**

1. **Track B's ceiling is disk and streaming rate, not memory.** 231 GB fits on `D:` (614 GiB free) and runs at 1-3 tok/s
   with `--load-mode mmap`; a knowledge run at that rate is measured in days, which Track B permits and Track A never
   would.
2. **Track A's ceiling is the KV term.** Any claim that "a bigger model would be better for coding" has to pay for its
   context first; at 131,072 an agent's KV is the same order as its expert cache, and that trade has already been measured.
3. **A track's row declares its budget**: `context_requested`, `kv_bytes_per_token` (or `unreported`), `kv_resident_tokens`,
   `cache_mib`, `context_used` for the actual prompt. A row without its context is unreadable in A and merely thin in B.
4. **Speed comparisons across the tracks are meaningless** - 84 tok/s with a 131k context is a different machine from
   1-3 tok/s with an 8k one, and the second is doing the job the first cannot.

## What has to be built before either track ranks anything new

1. **The coverage probe** (Track B's missing half, no GPU): it is the only way "will answer all questions" becomes a
   measurement rather than a label.
2. **Knowledge resolution**: either more items or a harder slice, so a 1-2 point gap can be called.
3. **A Track A tool-call probe** as a *load* check (2026-11-01, `#4879`: the packaged binary scored 10/10 on a
   tool-call probe where a locally compiled one scored 0/10, and the short-fact smoke passed both).

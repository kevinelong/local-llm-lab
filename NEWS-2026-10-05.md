## A. Decision models land in mainline (the biggest opening for us)

This is the one item that directly attacks our weakest track.

- llama.cpp v0.6.0, released 2026-10-05 (PRIMARY: github.com/ggml-org/llama.cpp
  releases/tag/v0.6.0): a new `/v1/systemone` server API for decision models
  (PR #29818), supporting `laya`, `julia-1`, `lev`, `openjev` (with vision),
  `kev`. The Clef decision model is also supported, text and vision. "Nimble"
  is added as a decision model (PR #29844).
- Ollama 0.35.0, released 2026-09-29 (PRIMARY: ollama.com/blog/ollama-now-supports-jev-style-decision-models):
  the same `/v1/systemone` endpoint, based on TypeSafe's Jev API. Three models
  today: `nimble` (9B, Bespoke Labs), `tev1` (4B, Together AI) and `tev1:0.8b`.
  Question types: `choice`, `noul` (yes/no), `score`. Vendor measurement: nimble
  9B averaged 91 ms per decision locally on an M5 Max.
- ggml-org has published GGUF builds: `ggml-org/Clef-GGUF` and
  `ggml-org/OpenJev-GGUF` (plus a "New in llama.cpp: Decision Models" post).

Why this matters here. Our decision screen has two known problems: (1) our
evaluation set is only 18 archived windows and single runs are not reproducible,
and (2) the latency gate. Current results: jeff 18/18 but warm p95 6.27 s FAIL,
0/4 stalls caught; gliner 18/18, p95 27.56 s FAIL, 0/4 caught; julia p95 0.82 s
PASS but 3/14 false alarms. Now:

- Bespoke Labs published a benchmark suite of 13 public datasets with human
  labels, 3,880 decisions, including a published Jev 1.13 run
  (github.com/bespokelabsai/nimble, docs/PUBLIC_BENCHMARKS.md). That is a much
  better labelled substrate than our 18-window set, and it is not our own labels.
- A 9B decision model at ~91 ms, or a 4B / 0.8B model, should sit far inside our
  3 s gate on the RTX 5070 -- IF it discriminates. Discrimination, not speed, is
  the open question.
- OpenJev now exists as a GGUF in mainline llama.cpp, so our earlier CPU OpenJev
  harness can be replaced by the standard server.

## B. Runtime refresh: our llama.cpp pin is two releases behind

We are pinned at b10883. Current: v0.5.0 (2026-09-24) = build b11146, v0.6.0
(2026-10-05) = nightly b11429.

- v0.6.0 (PRIMARY): new `llama_batch_ext` API plus `llama_process()` for mixed
  token/embedding batches; session format bumped to LLAMA_SESSION_VERSION 11 (a
  BREAKING change -- old session/state files may not load); Qwen4Exp high-quality
  support with MTP speculative decoding (~1.5x decode on DGX Spark); CUDA gains a
  model-driven W4A4 (NVFP4/MXFP4) matmul path (Blackwell-friendly, our sm_120);
  `llama_prefetch_rows()` MADVISE prefetch for Qwen4Exp/Gemma4 PLE tensors; ggml
  v0.26.0; Metal up to ~3x matmul.
- v0.5.0 (2026-09-24): CUDA `conv2d` implicit GEMM; Metal MoE/SSM_CONV fusion;
  DFlash2 speculative decoding (reported up to ~2x on long contexts); MiMo-V2.6
  conversion support; HunyuanOCR DFlash; Nemotron MTP; Qwen4Exp hyper-connection
  and sparse flash attention; Gemma 4 DSpark draft backbone and parsing fixes;
  sampling overridable via environment variables; `--host` accepts multiple
  addresses.

Relevance: the coding screen's throughput levers (DFlash2 / MTP spec decode) and
the Gemma 4 fixes are all in these two releases. The batch/session break means a
runtime bump is a deliberate, new-root change; do not retrofit it into a frozen
root.

## C. Prism / Bonsai (confirmations and one correction)

- PRIMARY (docs.prismml.com/run/llamacpp): 1-bit `Q1_0` and ternary `Q2_0` are
  merged into UPSTREAM llama.cpp -- use the `*-Q2_0_g64.gguf` files on a stock
  build. Ternary Bonsai 2 (`PTQ1_0` / `PQ2_0`) still needs the PrismML fork
  (`prism` branch) or its prebuilt binaries; a stock build either refuses the
  file or, for `Q2_0`, loads it silently and emits gibberish. The documented
  minimum is `prism-b10658`; our v8 runtime `prism-b10743` is newer, so our
  Swift Bonsai 2 PQ2 result stands.
- Bonsai 2 27B (base Qwen3.8-27B): 5.95 GB `PTQ1_0` or 7.21 GB `PQ2_0`, 98.2%
  of FP16 retention, 262K context. Packing choice is hardware-dependent:
  `PQ2_0` is the faster decode on Blackwell/Blackwell-class (our card),
  `PTQ1_0` is faster on Ada and the L4.
- No newer Bonsai release found. Our v8 result (Swift Bonsai 2 PQ2, events and
  ledger fully correct) remains the strongest local result in the series.

## D. Strata (staged pin is stale; vendor claims now corroborated)

- We staged engine v0.1.27 (2026-09-29). Current release is v0.1.39
  (2026-10-04); the repo is at ~13.6k stars and hit the HN front page on
  Oct 4. A 12-release gap.
- Corroborations since our review: the public README now states 32 GB of RAM is
  the minimum for the Coder build, and community reports confirm low-RAM mode
  works on 32 GB Windows PCs -- our staged plan is valid as written.
- Integration surface grew: Strata serves OpenAI `/v1`, the Anthropic Messages
  API, AND the OpenAI Responses API `/v1/responses` (tested against Codex CLI
  0.160.0). Our staged runner note should therefore be widened from one to three
  API shapes.
- New features relevant to us: `repeat_stop_tokens` (a reply repeating one token
  256 times is ended; default on) -- directly relevant to the MiMo repeated-
  reasoning loop we recorded; `vram_elastic` (hand VRAM back while idle);
  `"parallel": N` (opt-in; on a 12 GB card it cuts waiting but costs decode
  speed).
- Unchanged caveat: on a 12 GB card low-RAM mode is disk-bound. Any run here is
  a correctness and start-up test, not a speed test.
- To resolve before any run: our staged.json records apache-2.0 for the
  ISTA-DASLab GGUF repo, but the Qwen3.8-Flash-Next weights themselves are under
  the Qwen Community License 1.0 (hosted-service restriction). Confirm which
  licence actually applies to the Coder pack, and re-pin the engine binary and
  hashes to v0.1.39.

## F. Harness track

- DeepSeek Harness (dsh), MIT, released 2026-08-13 as a v0.1 developer preview
  (latest ~0.1.5-rc.3). Plugin-first ("everything is a plugin"), headless mode
  plus a local Web UI, MCP, sandboxes, skills, and an experimental Agent Teams
  runtime. Local models connect through OpenAI-compatible endpoint plugins
  (community-maintained). Explicit warning: breaking changes between preview
  releases -- pin the version you build against.
- Magnitude (magnitudedev/magnitude), Rust, an agent plus a built-in
  self-tuning inference engine that compiles kernels on-device; vendor claim
  "up to 2x faster than llama.cpp". One independent CPU measurement reported
  21x slower. Unverified here.
- Both are new-ecosystem entrants and would extend our harness set (Pi,
  OpenCode, Goose, mini-SWE-agent, OMP). Treat as preview.

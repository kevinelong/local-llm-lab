## 2. [GH] `#6208` is bisected: the 12 GB decode collapse is **the 0.2.8 revert of the routing prior**, and that default was worth **+22.9 % perplexity** - the speed was bought with quality

The issue we have carried since 11-18 ("0.2.15 decodes 28-36 % slower than 0.2.7 on an RTX 3060 12 GB") got its
answer today. **`0xluk`, 2026-11-22T13:09:49Z**, having bisected it:

> *"the last fast release is **0.2.7.1**, the first slow one is **0.2.8**, and the first slow commit is
> `20a63cf0f` ('Residency-biased routing (STRATA_ROUTE_PRIOR) is off by default again on 12 GB NVIDIA cards
> (#4402)'). Its parent is 0.2.7.1 itself. So the drop is the deliberate revert of the 0.2.7 default
> `STRATA_ROUTE_PRIOR=1.5` on cards of 13 GiB or less. Our '0.2.7-based' comparison build still had it on
> (its start log says 'residency-biased routing is on by default on this card'). I should have spotted that
> before filing."*

Two more reporters joined in the same thread in-window: **`kroll-j`, 2026-11-22T07:53:46Z**, *"I'm suddenly
getting around **17 tok/s** decode on an RTX 3060 12GB after upgrading to 0.2.18, compared to around **39
tok/s** before"*; and the 11-19 second reporter (`notfence`, RTX 4070, 50-100 -> 40-75 tok/s, ~1,500 -> ~1,400
experts in VRAM) is unchanged. The maintainer's 2026-11-20T12:47Z request for a 0.2.17 arm and both start logs
is what produced it.

**Why this is the useful correction and not just a resolution.** This lab measured the other side of that same
default on 2026-10-28: `STRATA_ROUTE_PRIOR=1.5` cost **+22.9 % teacher-forced perplexity**, top-1 **71.68 ->
67.30 %**, and argmax differing on **19 %** of positions, for **62.6 -> ~102 tok/s** at a 1K prompt. And on
2026-11-01, AIME 2026 **76.7 -> 66.7 %** for **+45 %** decode, plus `#5225`'s tool-call argument corruption.
So the 28-36 % decode "regression" on a 12 GB card is the price of the answers the lab said it wanted, paid
deliberately, and the 11-21 file's hit-rate story (`#6478`: **96.8 -> 64.5 %** from 0.1.53 to 0.1.63,
route-tail-skip recovering a third) has a **second named cause**.

*Consequence for the declaration: a Strata row on a card <= 13 GiB now reports `route_prior=` and
`route_tail_skip=` and the hit rate both produced, or it cannot be compared with a row from before 0.2.8. The
two locks are independent: prior (`20a63cf0f`, #4402) and tail skip (0.2.17 default).*

*Applies: directly, to rows we already hold. Instrument: the declaration edit plus one two-arm start reading
the engine's own `residency-biased routing` and hit-rate lines. Cost: an edit, then ~15 min.*

**`freriadoc/Avalon#70`** (2026-11-20T08:24:37Z, 0 comments, `status: lead` - second-hand from a fork's own
issue): RX 7800 XT **16 GB**, Windows, HIP, Qwen3.8-Flash-Next IQ3KS + MTP, `-c 262144 -b 32768 -ub 32768` -

to 0.02-0.04. The same command with `-ub 16384` or `-ub 8192` works correctly."* The log is the finding:

```
[moe-cache] CUDA0 free source=d3dkmt: hip=9925 MiB d3dkmt=8860 MiB (total 16176 MiB)
[moe-cache] CUDA0 loan plan: chunks MiB 7104 1744, 8848 MiB of 7125 free (largest gap 7125): **NO ROOM**
[moe-cache] CUDA0 borrow: 7103 MiB at 444 MiB of the slab ...
```

His reading of the code: the start-up reservation is planned at the full `n_ubatch`, `ubatch_fit()` only lowers
it per request above 512 tokens, and **when the borrow fails `ggml_backend_cuda_borrowed_buffer_type_alloc_buffer`
falls back to an ordinary device allocation** - so *"on Windows the fallback succeeds because Windows lets VRAM
be over-allocated"*, and the server carries on with an **8,848 MiB compute buffer** on a card whose free VRAM
the expert cache already took. Suggested fix: *"when the start-up loan plan reports NO ROOM, lower `n_ubatch`
until the prompt graph fits, or refuse to start"*.

**Two things transfer immediately.** (a) **A startup `NO ROOM` in the loan plan is a VOID before start, not a
slow row** - and it is the third engine (after Strata's `#4261`-family prints and llama.cpp's own no-cache line)
whose loader says a request cannot be honoured and then proceeds. (b) **`hip` and `d3dkmt` report the same free
VRAM 1,065 MiB apart**, and this lab's gate reads a single number.

Adjacent items in the same window, one line each: **`ROCM/rocm-systems#16035`** *"[HIP/CLR][Windows]
hipMemGetInfo ignores VRAM used by other processes"*; **`ooples/AiDotNet.Tensors#1803`** *"CUDA on WDDM: warn
when the pooled reserve exceeds physical VRAM (sysmem fallback hides OOM)"*; **`XuehaiPan/nvitop#242`** a
proposal to read per-process GPU memory on Windows (WDDM) from a performance counter - the same counter this
lab used for `GPU Adapter Memory\Shared Usage` on 10-22.

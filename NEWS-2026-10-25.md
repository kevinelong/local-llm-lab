### 2.1 What 0.2.5 changes on a 12 GB NVIDIA card - the part that is ours

Quoted from the 0.2.5 body, each with its own measured row:

- **Prompt chunks follow the card.** *"NVIDIA cards under 16 GB now read prompts in chunks of 4096 instead of
  8192: agent decode +2 %, an agent turn takes the same time, a cold 8K prompt is 9 % slower. AMD cards and
  cards with 16 GB or more keep 8192."* Our card is 12 GB, so **prefill moves down 9 % on a cold 8K prompt**
  and agent decode moves up 2 % - two numbers in opposite directions from one default, which is exactly the
  kind of change a single throughput figure hides.
- **The same prompt always takes the same path.** *"The engine now picks the prompt path from the prompt's
  length (96 tokens and more go through the chunked pass). The old timing guess changed answers between
  runs. Once the model is ready, the engine also warms up the chunked pass in the background."* Vendor also
  prices the warm-up it replaces: *"about 3.6 s on an R9700"* that a first prompt no longer pays.
- **The Qwen async tier is now self-measuring on one CUDA GPU with experts in RAM**: *"the engine now tries
  the asynchronous tier itself, measures it for 64 windows and keeps it only if it is not more than 2 %
  slower."* This is the `STRATA_ADAPT_OVERLAP` axis from #2936 arriving as an automatic decision rather than
  an env var, and it means a post-0.1.50 row cannot attribute its own overlap state without reading the log.
- **Fewer GPU launches per layer**: decode *"+13 % on one test PC in 5 of 5 pairs (same output every run),
  +2.4 % on one R9700 and +4.5 % on four."*
- **A model bigger than the card gets a longer start wait by itself**: *"10 minutes plus about 8 s per GB
  above 40 GB, at most 30"* (#3949, #3459) - relevant to the `startup_wait_expired` class we recorded on
  2026-10-22.
- **`strata update` fixes that touch our recorded failure modes**: it *"says 'the engine was NOT updated'
  when it was not"* (#3653), *"runs the new engine's test start with a short context"* (#3842) and *"keeps
  the CUDA build that runs on your PC"* (#3835).
- **One installer per system**: the Windows/Linux installers **no longer carry an engine** (*"On first
  start the app shows the engine for your graphics card with its size and one Download button"*). Windows
  installer `Strata-0.2.6-windows-x64-setup.exe` is **111,885,523 B**; the engine is a second download.

### 2.2 What 0.2.6 adds, and the one row that is on our card

- **DeepSeek "Speed" mode**: *"Faster uses 5 of the model's 6 experts per word... It is the default on a PC
  with 16 GB of graphics memory or less... On an RTX 5070, Faster mode decoded code and agent runs 16 %
  faster."* Flags: `--speed`, `--full-quality`, `--experts N`; needs DeepSeek engine 0.1.50 or newer. This
  is a **vendor row on our exact card**, for the DeepSeek engine, which we do not serve.
- **The RAM store can hold every expert** where free RAM allows: *"When all the CPU-side experts fit in RAM
  with 8 GiB to spare, the engine now copies all of them in at load and runs without the demand store (all or
  none, never a part)... On Windows the check also needs the commit room (RAM plus page file)."* The vendor
  names our shape explicitly as the negative case: *"A PC that cannot hold the whole set, such as a **46 GB
  RAM PC with a 12 GB card**, keeps the store as before and gets the same answers and speed."* Load time on
  the positive case rises (34 s -> 55 s for a 108 GB copy) - a second instance of "a memory win paid at
  load".
- **AMD HIP engines hang under WSL** and setup now says so; NVIDIA unaffected. Not us, recorded because we
  start WSL for `yt-dlp`.
- A monitor fix worth knowing when reading vendor speed rows: *"a one-token probe used to read 1,250 tok/s in
  the monitor"* - the UI number class the 2026-10-21 file already ruled out of any quoted rate.

### 2.3 What it forces, in this lab's terms

- **Bump target: engine 0.1.50** (Qwen), Control 0.1.51 if the app moves. Yesterday's file priced 0.1.48;
  the bytes changed, so **the download is new**, and the declaration list from 2026-10-24 stands with two
  additions: **prompt chunk (4096 on this card)** and **the fact that prompt-path selection is now
  length-based**.
- **No prefill row crosses this boundary.** 0.1.48-and-earlier prefill numbers were taken with 8192-token
  chunks on a card under 16 GB; a post-bump row uses 4096. The vendor's own row prices the difference at
  **-9 % on a cold 8K prompt**, which is the same order as the effects our throughput protocol resolves.
- **The `--vram-reserve-mib 1536` default and #3952's spiral are unaddressed in either release body.** The
  words "reserve" and "VRAM free" appear in neither 0.2.5 nor 0.2.6 notes; #3952 is still open and still has
  no maintainer reply (§3.8).

### 2.4 The determinism sentence, taken seriously

Our record contains three separate readings that "temperature 0 is not seed-stable on this engine"
(2026-10-05 probe, the 2026-10-11 three-identical-probe exception, and the 2026-10-12 placement result where
**65 of 93 justifications differed but 0 of 93 letters**). 0.2.5 supplies a mechanism for the first and third:
a path chosen from measured round times cannot reproduce. Consequences to record rather than act on:

- **A/Bs whose claim rests on "same flags, same text" must name the engine version**; before 0.1.50 the
  correct declaration is "non-deterministic by policy", after it the claim is at least testable.
- **The 0.2.5 identity claims are narrow**: *"same answers (KL 0.10204 against 0.10203)"* is quoted for
  Strix Halo's matrix units, and *"same output every run"* for the launch reduction - neither is sm_120.
- `[INFERENCE]` The mechanism also explains why our **0.1.47 q2_0 pack** answered **"2, 3, 5, 7, 11" on
  every request** in the 2026-10-22 A/B: a short, low-entropy answer is the case where a path change cannot
  show, which is why the A/B was text-neutral and told us nothing about determinism either way.

### 4.2 [VRAM] #28633: quantised KV on a default CUDA build - what the source actually says

**Source.** Issue **#28633**, **open, 5 comments**, created 2026-09-09T08:00:37Z; **newest comment

### 10.1 [ARX] 2610.31646 "Low-Bit N-Gram Embeddings for Language Models" - why the 110.6 GB Engram file is IQ4_NL

Stephen Chung, Wenyu Du (2026-10-22T17:59:51Z or earlier in the batch). Abstract, quoted: *"DeepSeek-V4.1-Flash,
for example, allocates **196 billion parameters** to its Engram n-gram memory... Across nanochat-, Llama-, and
GPT-2-family models trained from scratch, **four-bit tables save approximately 75 % of table memory** while
preserving more than 99 % of the validation-loss improvement... **on DeepSeek-V4.1-Flash and
Qwen3.8-Flash-Next, low-bit tables save 47-55 % of table memory, with perplexity increases of less than
1.2 %** and largely preserved downstream task performance."* It also finds *"a short fine-tuning phase
recovers a significant part"* of going below four bits, and that *"reinvesting the saved memory in larger
tables can improve performance beyond that of the original full-precision tables"*.

**Why it matters here:** the shipped Engram file is **IQ4_NL 4.50 bpw** on 196.6B parameters - exactly the
operating point this paper argues for - so the largest single component of the biggest download in this lab is
already at the paper's recommended precision, and the remaining headroom (3-bit, plus fine-tuning) is not
something a downloaded pack can exploit. It also means **the Engram bytes are not where a fidelity loss should
be looked for**; the backbone is. `[INFERENCE]` And because the tables are *"read sparsely, one row per
token"*, the read pattern is random-row on a 110.6 GB file: this is a **disk-latency** cost, not a bandwidth
one, which is a different gate from anything in our current protocol.

### 10.2 [ARX] 2610.31098 "RIFT: KV Cache Compression for Draft Models" - decode staleness

Dor Tsur, Maor Ashkenazi, Maximilian Golub. *"Compression methods that focus on prefill information can lose
relevance as the output length grows. We term this phenomenon **decode staleness** and show it degrades draft
model accuracy under selection-based KV cache compression... refreshing the KV cache selection during token
generation significantly improves the drafter's quality."*

**Why it matters here:** it is the mechanism behind a drafter that looks fine on a short A/B and degrades in a
long agent turn - i.e. a fourth reason a single-pair drafter comparison is void, beside the 18 % session
drift (§3.3), the verify-scratch VRAM (§5.1) and Strata's own 567-slot cost. Not testable here: we do not
control selection in the drafter's KV.

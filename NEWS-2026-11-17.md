## 1. [GH] Strata `#6136`: engine 0.1.60 re-reads an **entire chunk** whenever a few tokens are appended, and that is the agent-turn path

This is the day's item. It is the first report that explains *why* the 0.1.60 prompt numbers disagree
(`#6074` at -13 %, `#6091` at +28 %, the vendor's 5070 Ti at +48 %), and it lands on the workload this lab
actually runs: a long prompt, then a short appended tail.

- **Filed 2026-11-17T07:27:29Z, 0 comments.** Engine **0.1.60** (`BUILD.json` commit `09b603886925`), compared
  against **0.1.54** back to back on the same machine, same model, same config. RTX **4080 16 GB** (sm_89),
  Ryzen 7 7800X3D, 64 GB DDR5, Windows 11, driver 617.42. Model Qwen3.8-Flash-Next **GSQ-RCO IQ3_XXS** native
  pack + PLE, MTP `--spec 6`, `--max-context 262144`, `--resident-budget-gib 40`.
- **The measurement, their own harness, a fresh engine start per arm, 2 runs per arm**, 66,968-token prompt then
  the same prompt with ~9 tokens appended:

| | 0.1.54 | 0.1.60 | change |
|---|---:|---:|---:|
| first read, 66,968 tok | 3,554-3,592 tok/s | **3,852-3,862** | **+7.5 %** |
| identical prompt resent | 715-748 ms | **41-44 ms** | **17x faster** |
| **prefix + 9-token tail** | **810-853 ms** | **5,276-5,296 ms** | **6.4x slower** |
| weighted decode (3 scenes 93/5/2) | 98.8-109.9 tok/s | 110.1-113.7 | +7.0 % |

  Every turn of a long conversation pays ~4.4 s more, on a workload whose *identical* resend got 17x faster.
- **The mechanism, read from the v0.2.14 source (`git clone --depth 1 --branch v0.2.14`).**
  `include/strata/prefill/equal_cut_rule.hpp:103-112`, `equal_chunk()`:
  `const int64_t per = tokens / n + (tokens % n != 0);` - `per` is derived from the **token count**, so appending
  nine tokens moves every chunk boundary. Checkpoints exist only at chunk boundaries
  (`src/program/generate.cpp:13693`, `src/prefill/prefill.cpp:7325`), so the last one sits at `(n-1)*per` and
  everything after it is re-read. Their log makes it visible:
  `append : prompt 66977 tokens = 50223 reused + 16754 read in 5237 ms, 4 checkpoints` - **16,754 = 66,977/4**,
  exactly one equal chunk. 0.1.54's `Cut::today` used full chunks plus a remainder, so only the remainder moved.
- **What they tried, and what worked.** `--prompt-cache-every 8192`, `--prompt-cache-spread`, `--prompt-cache-tail`,
  `--prompt-cache 12`, `--prefill 8192`, `--prefill 6144` **all failed to change the 16,754** (the checkpoint count
  is set by the chunk count, not by `--prompt-cache`); making the chunk smaller made the drift worse and the first
  read 44 % slower. **`STRATA_PREFILL_EQUAL=0`** drops the re-read to **1,697 tokens / 2,629 ms**, and
  **`EQUAL=0` + `STRATA_PREFILL_CPU_SHARE=0`** to **161 tokens / 1,490 ms**.
- **It does not fully recover, and they say so:** append is still **1,481-1,497 ms against 810-853** (+79 %), and
  the residue is a *fixed* cost in the small-tail resume path - 161 tokens taking 1.5 s (~9 ms/token) where the
  first read runs at 0.25 ms/token. They explicitly decline to file a patch: checkpoints cannot exist mid-chunk
  because K/V is computed layer by layer.
- **Applies to us: as a bump gate, not a curiosity.** Our arms are agent turns with long prefixes, and this is the
  first Strata number that separates *first read* from *append*. It also reframes `#6074` from the 11-16 file: the
  "trailing chunk" hypothesis and this `per = ceil(tokens/n)` boundary drift are the same phenomenon seen from two
  ends - `#6074` measured a first read of a 20,000-token prompt, this measures the second turn of a 66,968-token
  conversation, and **both are chunk-boundary arithmetic**.

## 2. [GH] `#6074`'s thread supplies the missing control: **the engine's auto cap is not the same in 0.1.59 and 0.1.60**, so cross-version prompt rates are confounded

`#6074` (from the 11-16 file: -13.0 % at 20,000 tokens on an sm_120 16 GB 5080) went from 12 to **17 comments**,
and the additions are the most useful part. Reproduce them as method, not as verdicts:

- **`@ShaggyDragon`, 2026-11-17T05:47:50Z:** *"our production engine **0.1.59 auto-caps at 17,664** on this card and
  **0.1.60 at 17,920** - both bare `auto`, no pin. Every fixed token count therefore has two different shapes
  depending on the arm, which is part of why my earlier 20K number and yours were never quite the same
  measurement."* Their A/B/A2 (drift <=0.7 %, `reused` 0 on all 75 reps): **15,880 +6.2 %; 17,772 +19.7 %;
  19,686 -9.3 %; 19,906 -9.3 %.**
- **`@jesse890423`, 2026-11-16T20:08:35Z:** at an 8,192 cap on both engines, a step just past `2 x 8,192 + 2,048`:
  **8,546-8,710 +2.0 %, 10,182-10,369 +2.0 %, 16,728-16,935 +1.7 %, 18,374-18,544 -9.3 % with two modes** - "a gain
  at `cap + 2K`, a loss at `2*cap + 2K`".
- **`@mercant1982`, 2026-11-16T21:36Z and 2026-11-17T07:31Z:** with **both actual caps pinned at 16,384** (24
  cold-prompt requests, ABBA, two CMP 170HX cards), **+7.5 % / +9.2 % / +9.0 % at 16,384 / 18,432 / 22,528**, and
  decode **162.5->164.5**, **150.7->154.3**, **149.1->153.9 tok/s**. Both declare "outputs differ and quality is
  ungraded".

**What this changes for us:** our rules already say a row must read the *granted* chunk back from the engine. This
is the sharpest evidence yet for why - the same prompt length is a different number of chunks on the two engines,
so an A/B that fixes the *prompt* and not the *cap* compares two workloads. It also means the -13 %/+19.7 %/-9.3 %
spread in one thread is not a contradiction, it is a function of where the prompt sits relative to a cap the engine
chooses. **[INFERENCE]** our own 11-16 A/B design (16K / 20K / 40K) is sound only if each arm's cap is read back and
reported; 16K and 20K can land in different chunk counts on 0.1.59 and 0.1.60.

## 3. [GH] Strata `#6128`: on 0.1.60 the expert cache can grow **past its own auto estimate**, and then decode collapses - the reserve is a guard now, not a tax

- **Filed 2026-11-17T02:25:59Z**, source install, RTX **4090 24 GB**, Windows 10 22H2, driver 621.01, Qwen3.8-Flash-Next
  Coder IQ1_M, `--max-context 262144 --kv int8 --kv-resident 32768 --expert-cache auto --prefill auto --spec 4`,
  MTP, `--vision`. Two starts at `--vram-reserve-mib 700`, two at 1500.
- **The table, from the engine's own log lines:** at reserve 700, engine 0.1.60 logs `expert cache auto: ... -> 6222
  slots`, then a single `shrinking` line, and **ends at 7,961-8,106 slots (15.15-15.43 GiB)** - larger than its own
  auto estimate - with **0 MiB free** on the first start and **0.2 tok/s** (52 tokens in 423 s); the second start at
  379 MiB free decoded **19.2 / 41.5 / 25.9**. At reserve **1500** the final cache stays **7,447-7,522 slots** and
  decode is **97.0-138.6 tok/s**. Engine 0.1.50 at the same 700 reserve ended at 7,192-7,500 slots and decoded
  129-162.
- **A confirmation on a different card and reserve** (`@pietroMastro92`, 2026-11-17T07:04:56Z): RTX 4000 Ada **20 GB**,
  Windows 11, `--vram-reserve-mib 1024`, IQ3_S native, final cache **4,695 MiB** against a 2,387-slot auto estimate,
  **4,325 MiB free**, **42.3 tok/s** - "at 1024 the final cache stays *below* the auto estimate, as in 0.1.50". The
  same card reads **+12.7 % on a 945-token prompt and +12.8 % on 4,830** against 0.1.59.

**Applies to us with a sign flip we have to declare.** Our own reserve sweep (**2026-11-01**, engine 0.1.47, 9 arms)
concluded *"900 MiB beats 2,000 by +9.9 tok/s (+12 % of decode)"* because a reserve is a near-1:1 tax on the expert
cache. On 0.1.60 the same lever has a **lower bound**: too small a reserve lets the cache overshoot its own estimate
and the decode collapses by 3-4x. So the 900 advice is a **0.1.47** result, and a bump row declares a reserve that
keeps the final cache at or below the auto line - which is a *read-back* condition, not a number.

## 5. [GH] llama.cpp `#28111`: on SM120, IQ-quant `mul_mat` is not batch-invariant at **n = 5 and n = 8** - and those are verify-window sizes

Long-standing (opened **2026-08-31**), updated in-window, and it is our compute capability.

- **The test and the result:** one batched `ggml_mul_mat` against a serial chain of single-column calls, `memcmp` at
  `max_err() = 0`: **`iq3_s` m=17408 k=5120, `iq4_xs` m=10240 k=5120, `iq4_xs` m=5120 k=17408` all pass at
  n = 1..4 and all FAIL at n = 5 and n = 8**, `ERR` 1.0 against a tolerance of 0. Reporter's frame: *"This matters
  for speculative decoding, which is lossless under greedy sampling by construction... the verification pass must
  agree with what one-token decoding would have computed."*
- **Two independent reproductions in the thread:** `@siavashnorouzi` on **2026-10-02** (`RTX 5090, SM120`, master
  `207bdab950`, *"still reproducible"*, and *"forcing the number of warps at 2 or 4 irrespective of `n` fixes the
  issue"*), and `@Incorrectone` on **2026-10-17** (`RTX 5060 Ti 8 GB`, latest git build, `M=10240 K=5120`).
  `@mndodd` reports the same class on SYCL. The MMVQ/MMQ crossover is **not** the cause: lowering it makes it worse
  (3/18 at the equivalent threshold 1, because the two sides then run different kernels).
- **Still open, no fix in the window.**

**Applies to us precisely, and the precision matters.** Our card is an RTX 5070 = **sm_120**, and n = 5..8 is the
verify window a drafter produces (`--spec 4` gives 5 rows; the 11-15 MTP row ran acceptance 57.71 %, i.e. windows
of 5-7). **But the failure is stated for `iq3_s` and `iq4_xs`** - our llama.cpp rows are **Q4_K_M** (K-quant) and
our Strata `q2_0` is a native pack, neither of which is IQ. So no recorded row is invalidated; what this earns is a
declaration: **a speculative row names the weight quant *types* in the verify path**, not only the pack name, and our
**gated** IQ packs (the ISTA `IQ2_XXS` download) would be exactly the affected class.

## Shortlist, cheapest first

1. **Make *append* cost a first-class metric and declare the two switches that bound it** (`#6136`). Engine 0.1.60
   re-reads **16,754 tokens of a 66,977-token conversation** on a 9-token append - one whole equal chunk - because
   `equal_chunk()` derives its chunk size from the token count, so every boundary moves. `STRATA_PREFILL_EQUAL=0`
   takes the re-read to 1,697 tokens, adding `STRATA_PREFILL_CPU_SHARE=0` to 161, and **append is still +79 % over
   0.1.54** because of a fixed ~1.5 s resume cost. Our arms are agent turns; a bump row that reports first-read
   speed and not append speed reports the half that improved. (An edit to the declaration template.)

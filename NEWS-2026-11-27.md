## 1. [GH] The 0.1.69 Windows crash now has a named cause and a switch: a start-up step that discards a buffer pool on GGUF packs

`#7245` (created **2026-11-26T14:39:12Z**, 3 comments, maintainer answered **15:19:56Z**) is the
same fault offset the 11-26 file carried as `#7206`'s CUDA reporter - **`strata.exe+0x6fbc8b`,
`0xc0000005`** at 0.1.69 - and the vendor has now resolved it with symbols.

**The report.** Windows 11 26100, RTX 3060 **12 GB**, sm_86, driver 610.88, engine
`0.1.69-windows-x86_64-cuda-cuda13`, Qwen3.8-Flash-Next GSQ-RCO IQ3_S as a **native + `--ple-gguf`
split**, 262144 context, `--kv int8 --kv-resident 32768 --vram-reserve-mib 1536`,
`--expert-cache auto`. **Eleven WER events on 2026-11-26, all at the identical offset**, 4-6 minutes
into each session; a twelfth exit logged only as "stopped unexpectedly". Roll back to **0.1.65 with
31 identical arguments** and the same 6,440-token prompt serves and keeps serving.

**The vendor's answer, in their words** (paraphrase kept close because it is the mechanism):

- `0x6fbc8b` is the `rep movsb` inside the C runtime's `memcpy` - "the engine copied a block of
  memory into a buffer that was too small".
- **Since 0.1.67**, models read from their GGUF files in place go through a start-up step: the model
  files are closed, the start-up reads run unbuffered, and the files are mapped again. **0.1.65
  refused to do that for GGUF packs**, which is why 0.1.65 is stable on that box.
- "The last part of that step throws away a pool of buffers and sets their size to zero." A GGUF
  pack needs that pool for every expert neither in VRAM nor in the RAM copy; the next such expert
  gets a zero-size buffer and "about 1.5 MB are copied into it".
- Their read fits the log: the first small request works (all its experts are in the RAM copy) and
  the first big prompt dies - 44.4 of 54.8 GiB resident, 23,147 expert blobs streamed on a
  6,440-token prompt.
- **They do not think the small-card prompt rule, the fused kernels or the 17 sm_86 switches are the
  cause.** The fix "is small and is written ... will come as a Windows engine update. We cannot give
  a date."

**The switch to try while staying on 0.1.69: `STRATA_STARTUP_UNBUFFERED=0`** (turns the start-up
step off; "only makes the start-up fill a bit slower"). They ask for two log lines back - "the GPU
cache's fill and the RAM copy read unbuffered" and "the startup reads are done: experts.bin mapped
again" - and a minidump only if it still crashes.

**Does it apply here?** Yes, as a **bump condition**, and not to any row we hold:

- Our installed engine is **0.1.66**, which the vendor's "since 0.1.67" statement places *before*
  the step - so the Strata row measured on 2026-11-24 (our `inkling2_loop` GGUF at 28.3 tok/s) is
  not exposed. That is an inference from their sentence, not a measurement on our box: **the check
  is our engine's own start-up log for those two lines**, which we have never grepped for.
- The declaration for any bump to 0.1.67+ must carry **`STRATA_STARTUP_UNBUFFERED=0`** for any
  GGUF-pack arm and name the **pack layout** (native pack + `--ple-gguf` split vs a converted
  `experts.bin`) as a field, because 0.1.65 refuses the step for one layout and 0.1.67 does not.
- The 11-26 crash-triage switches (`STRATA_PIN_BY_NEED=0`, `STRATA_ARENA_PIN_GIB=8`) are **not**
  the remedy for this class: this one is in the file tier, and the reporter's own `STRATA_PF_SMALL`
  / `PF_SMALL_FUSED` / `PF_FUSED=0` ideas are untested by the vendor for it.

## 4. [GH] Inkling vision: the encoder runs on the CPU on Windows/CUDA, and an image chat re-encodes every image and re-reads the whole prompt

Two reports, one day apart, both scoped to files and line numbers.

`#7288` (27 Nov 05:06Z, Windows 11, RTX 5060 Laptop **8 GB**, Inkling-2-Mini Q4_K_M + Vision, CUDA
13): a 1280x720 screenshot costs **~20 s** before the first token, and a picture already in the
conversation is read again on the next turn. Cause traced to `ink_vision.h` - no ViT kernels for
Inkling on CUDA, so "the encoder runs on the host and keeps the weights as float" (**a 1.27 GB
float staging copy**), with no `STRATA_INK_VISION_CUDA`-style switch. The reporter's own patch
(fp16 weights uploaded once, encoder on the card) measures **20 s -> 3-5 s** on the same
screenshot. The release's own CPU-path table is quoted in the same issue: 0.25 MP 15 s, 1 MP 74 s,
2.1 MP 334 s, 3 MP 743 s.

`#7303` (27 Nov 12:25Z, RTX 3090 + 4060 Ti, Ubuntu, `strata-inkling` 0.1.69, SQ-20 + Vision, 512K,
`--kv fp8 --draft dspark`): after a 5-image question, a **follow-up with no new images** still costs
the full wait, with `strata-inkling` at **~1,600 % CPU**. From `engine/src/inkling2/ink_serve.h`
v0.2.22-1: the encode loop at **~line 645** runs over every image in the request on every turn (no
embedding cache), and the prefix-reuse check at **~line 671** is wrapped in
`if (pg.images.empty()) { ... }` - "once a chat contains one image, every later turn also re-reads
the full prompt". Their fix proposal: an image-embedding cache keyed on the decoded pixels plus
grid size, and image-aware prefix reuse keeping a hash per image-pad position.

**Does it apply here?** Directly to how our vision rows read, and it invalidates a shape rather than
a number: **an image-chat turn is not an append**, so `reused` near zero on a vision row is expected
by construction and cannot be reported as an engine property. The instrument is one vision row with
a **follow-up turn that carries no new image**, reading (a) time to first token, (b) the CPU share
of `strata-inkling`, (c) `reused` from the request line. Cost: one engine start and two requests,
~15 min, gated (it is inference).

## 5. [GH] `#7301`: a learned expert profile is filed per pack tag, so a quant tier change starts over - the loader only checks geometry

Engine 0.1.62, Windows, RTX 3090 24 GB, Qwen3.8-Flash-Next 48 layers x 512 experts across three
tiers (UD-IQ4_XS v31 native, UD-Q4_K_XL, Swift IQ3_S_G8), `--adapt-every 1 --adapt-swaps 160
--adapt-decay 0.97`, config `expert_profile_save` / `expert_profile_save_every: 5`.

Training a profile on tier A writes `expert-profile-learned-<tag>.bin`; pointing the config at tier B
makes a **second** tagged file and the first start begins from the shipped baseline, because
`learned_profile_args()` substitutes the saved profile only when that exact path exists and matches:

```python
learned = profile_shape(save if os.path.isabs(save) else os.path.join(here, save))
base = profile_shape(args[i] if os.path.isabs(args[i]) else os.path.join(here, args[i]))
if learned is not None and learned == base:
    args[i] = save
```

`read_expert_profile()` (`src/core/expert_cache.cpp`) rejects only on magic, `version != 1`, and
`nl != n_layers || ne != n_expert`; it never compares pack, quant or weight hash, and `slots` is not
a constraint. **The four profile files on that box have identical headers** - `STRP`, version 1,
48 layers, 512 experts, 24,576 slots, 24,576 ranked - so nothing in the format is tier-specific.
Two asks: adopt any same-geometry `STRP` v1 in the directory with one log line, and document the
portability. The reporter's caveat is explicit: reuse is **inferred from the acceptance rule, not
observed**; "verifying it is one cold start and one log line".

Also in it, a number we have wanted: with `--adapt-decay 0.97` (half-life ~23 adaptations instead of
~2) hit rates "stay at **91-96 %** across mixed work", against the 0.7 default's over-specialisation
that `#6200` describes. He has not run the 0.7 arm, and says so.

**Does it apply here?** Our learned profile is a **196,632-byte `STRP` file, 48 x 512, sha256
`3acf05d1...`** (2026-10-16), the same geometry as the shipped one (`8f59b4aa...`). So the portability
claim is about our own file, and the test is a config line plus one cold start that prints
`pre-filled N of N slots from the profile`. It also settles the 11-16 question about whether a
profile helps: a profile that is silently not used is a null with a cause.
